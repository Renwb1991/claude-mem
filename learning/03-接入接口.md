# 第三层 · 懂它怎么接入 Claude Code（接口视角：使用与原理的交界）

> **目标**：理解「插件是如何被 Claude Code 调起来的」——这是使用与原理的分水岭。
> **方法**：这一章第一次真正打开代码，但只读**接口层**——从「Claude Code 触发一个 hook」到「调 worker 的一个 HTTP 接口」这一段。worker 内部怎么压缩/检索，留给第五、六层。
> **一句话定位**：**接口层的唯一职责，是把 Claude Code 的「hook 协议（JSON over stdin/stdout）」翻译成 worker 的「HTTP 请求」，再把 worker 的回应翻译回 hook 协议。** 它是「适配器 + 分发器」，不做业务。

## 8. ⭐ hook 生命周期总入口 —— `plugin/hooks/hooks.json`

第二层我们解析出了「hook→子命令」真值表，这里补上**每个 hook 在 shell 层到底执行了什么**。

### 8.1 一条 hook 命令的真面目

`hooks.json` 里每条 hook 的 `command` 都是一长串 bash，但剥掉「找插件路径」的样板后，核心永远是这一句：

```bash
node <plugin>/scripts/bun-runner.js  <plugin>/scripts/worker-service.cjs  hook claude-code <event>
```

拆开看：
- `bun-runner.js`：确保用 Bun 运行（找不到 Bun 会自动装）。
- `worker-service.cjs hook claude-code <event>`：**这才是入口命令**——子命令 `hook`，平台 `claude-code`，事件 `<event>`。
- 这两个参数 `claude-code` 和 `<event>`，正是第 9 步 `hookCommand(platform, event)` 的两个入参。

> 💡 注意：hook 命令**不直接干活**，它起一个短命进程，进程内向 worker 发 HTTP，然后退出。这印证了第二层「hook 是薄壳」的判断。

### 8.2 真值表（本机实测，再钉一次）

| hook 事件 | matcher | 事件名 `<event>` | async | 归属 |
|---|---|---|---|---|
| `Setup` | `*` | version-check（非 handler） | | 装配 |
| `SessionStart` | `startup\|clear\|compact` | 先 `worker start`，再 **`context`** | | **读取**（注入） |
| `UserPromptSubmit` | `*` | **`session-init`** | | 记录 + 语义注入 |
| `PreToolUse` | `Read` | **`file-context`** | ✅ | 辅助（文件历史） |
| `PostToolUse` | `*` | **`observation`** | ✅ | **写入**（抓观察） |
| `Stop` | `*` | **`summarize`** | ✅ | **写入**（摘要） |

几个关键细节：
- **`SessionStart` 挂了两个 hook**：先确保 worker 起来（`worker start`），再拉上下文（`context`）。顺序有意为之。
- **写入类都是 `async`**：Claude Code 不等它们完成，所以你感觉不到卡顿——记忆是「后台默默写」。
- `matcher` 决定触发范围：`PreToolUse` 只在 `Read` 时触发（`file-context` 只关心读文件），`PostToolUse` 是 `*`（每个工具都抓）。
- `hooks.json` 里**没有**为 claude-code 配 `user-message` 和 `file-edit`——它们是给别的平台/场景用的 handler（第 10 步会说明）。

> ✅ **本步小结**：每个 hook = 一句 `worker-service.cjs hook claude-code <event>`。`<event>` 决定进哪个 handler；`matcher`/`async` 决定触发范围与是否阻塞。

## 9. 分发与统一响应 —— `hook-command.ts` + `hook-response.ts`

`worker-service.cjs hook claude-code <event>` 最终进入 `src/cli/hook-command.ts` 的 `hookCommand(platform, event)`。这是**所有 hook 的唯一咽喉**，值得逐段看。

### 9.1 一次 hook 调用的完整管道

核心管道在 `executeHookPipeline`（`hook-command.ts`）：

```
readJsonFromStdin()              ← ① 从 stdin 读 Claude Code 传来的原始 JSON
   ↓
adapter.normalizeInput(raw)      ← ② 平台适配器归一化成 NormalizedHookInput
   ↓  input.platform = 'claude-code'
handler.execute(input)           ← ③ 分发到对应 handler，返回 HookResult
   ↓
emitModelContext(adapter, result)← ④ 经适配器格式化，写回 stdout（唯一的 stdout 出口）
   ↓
exit(result.exitCode ?? 0)       ← ⑤ 退出
```

对应「入参出参」这个本层核心问题：
- **入参** = stdin 的 JSON（Claude Code 给的），归一化成 `NormalizedHookInput`。
- **出参** = handler 返回的 `HookResult`，格式化后写回 stdout（Claude Code 读它）。

### 9.2 三个关键抽象

**① `NormalizedHookInput`（`cli/types.ts`）——统一入参**

不同 IDE 传来的字段名不同，适配器负责抹平。看 `claude-code.ts` 适配器：

```ts
sessionId: r.session_id ?? r.id ?? r.sessionId,   // Claude Code 用 session_id
toolName:  r.tool_name,
toolInput: r.tool_input,
transcriptPath: r.transcript_path,
...
```

归一化后所有 handler 都只认 `NormalizedHookInput` 的驼峰字段（`sessionId`/`toolName`…），**handler 因此与具体 IDE 解耦**——这就是 claude-mem 能同时支持 Claude Code / Codex / Cursor / Windsurf / Antigravity 的关键（`adapters/` 下每个平台一个文件）。

**② `HookResult`（`cli/types.ts`）——统一出参**

handler 只返回这个结构，关键字段：

| 字段 | 含义 | 流向 |
|---|---|---|
| `continue` | 是否让 Claude Code 继续 | 控制 |
| `suppressOutput` | 抑制默认输出 | 控制 |
| `hookSpecificOutput.additionalContext` | **注入给模型的上下文** | → 模型（MODEL_CONTEXT） |
| `hookSpecificOutput.hookEventName` | 声明这是哪个 hook 的输出 | 协议要求 |
| `systemMessage` | **给用户看的提示** | → 用户终端（USER_HINT） |
| `exitCode` | 退出码 | 控制 |

> 💡 **这解释了第一层的现象**：「下次会话开头多出来的那段上下文」= 某个 handler 返回的 `additionalContext`；「终端里那条 Claude-Mem 提示条」= `systemMessage`。二者分流，一个喂模型、一个给人看。

**③ IO 纪律（IO Discipline，issue #2292）——为什么 handler 不许自己 print**

`hookCommand` 一进来就 `installHookStderrBuffer()`：**执行期间缓冲所有 stderr**，只有在明确要「上报」时才 flush。原因：Claude Code 会把 hook 的 stdout 当协议、stderr 当反馈，第三方库乱写一行就会污染模型上下文。

所以每个 handler 文件顶部都有这句注释：

```
this handler is PURE ... MUST NOT call process.stderr.write / process.stdout.write / console.* / process.exit
```

**handler 只返回数据，所有 IO 由 `hookCommand` 统一管**。这是整个接口层最重要的设计约束，读 handler 时会反复见到。

### 9.3 错误处理：失败也要「优雅」（`hookCommand` 的 catch 块）

hook 跑在你每次操作的关键路径上，**绝不能因为记忆系统挂了就打断你写代码**。所以 catch 分了四类：

| 错误类型 | 判定 | 处理 | 退出码 |
|---|---|---|---|
| 适配器拒绝输入 | `AdapterRejectedInput`（如 cwd 非法） | 返回 no-op，静默跳过 | 0 |
| 输入不可用 | transcript 路径缺失 | 返回 no-op，静默跳过 | 0 |
| **worker 不可达** | `isWorkerUnavailableError`（ECONNREFUSED/超时/5xx/429…） | 记一次失败计数（fail-loud，连续 N 次才上报），静默 | 0 |
| 其他真错误 | 兜底 | flush 错误到 stderr + 发遥测 | **2（BLOCKING_ERROR）** |

退出码只有两个（`hook-constants.ts`）：`SUCCESS: 0`、`BLOCKING_ERROR: 2`。

> 关键设计：**worker 挂了 → 退出 0**（不是报错）。注释点明原因：退出非 0 会让 Windows Terminal 不断堆积标签页；而「连续失败 N 次才 fail-loud」保证真出问题时你仍会被告知。这是「优雅降级」的教科书写法。

`hook-response.ts` 则提供了那个最常见的成功响应常量：

```ts
export const STANDARD_HOOK_RESPONSE = JSON.stringify({ continue: true, suppressOutput: true });
```

> ✅ **本步小结**：`hookCommand` = 读 stdin → 适配器归一化 → 分发 handler → 格式化写 stdout。三大抽象：`NormalizedHookInput`（统一入参、解耦 IDE）、`HookResult`（统一出参、模型/用户分流）、IO 纪律（handler 纯函数，IO 集中管）。错误一律优雅降级，只有真 bug 才退出 2。

## 10. 七个处理器 —— `src/cli/handlers/`（按触发顺序）

`handlers/index.ts` 是一张注册表，把 `<event>` 字符串映射到 handler；未知事件返回 no-op。下面按「你实际会经历的顺序」逐个看，每个只回答三件事：**入参 / 调哪个 worker 端点 / 出参**。

### ① `session-init`（← `UserPromptSubmit`：你发消息时）

- **入参**：`sessionId`、`prompt`、`cwd`
- **前置门禁**：无 sessionId / 项目被排除(`shouldTrackProject`) / 是 `<private>` 等内部协议载荷 → 直接跳过
- **主调用**：`POST /api/sessions/init { contentSessionId, project, prompt, platformSource }`
  → 返回 `{ sessionDbId, promptNumber, skipped, ... }`（在 worker 里登记这条 prompt）
- **可选语义注入**：若开了 `CLAUDE_MEM_SEMANTIC_INJECT` 且 prompt 够长 → `POST /api/context/semantic { q: prompt, ... }` → 拿回相关记忆文本
- **出参**：有语义结果时返回
  ```ts
  { hookSpecificOutput: { hookEventName: 'UserPromptSubmit', additionalContext } }
  ```
  否则 `{ continue: true, suppressOutput: true }`

> 作用：**记录你的每条提问**，并（可选）按提问语义即时注入相关记忆。

### ② `context`（← `SessionStart`：会话开始时）

- **入参**：`cwd`、`platform`
- **主调用**：`GET /api/context/inject?projects=<所有相关项目>` → 返回一段拼好的上下文字符串
- **附加**：
  - Codex 平台走 MCP 工具 `session_start_context` 取（而非 HTTP）
  - 检测到 OAuth token 过期标记 → 在上下文前加一条提醒
  - 开了 `CLAUDE_MEM_CONTEXT_SHOW_TERMINAL_OUTPUT` → 额外拉带颜色的时间线，拼进 `systemMessage`，并附上 `http://localhost:<port>` 观看链接
- **出参**：
  ```ts
  { hookSpecificOutput: { hookEventName: 'SessionStart', additionalContext }, systemMessage? }
  ```

> 作用：**这就是「下次会话开头多出来的那段上下文」的生产者**——主线读取半环的接口端。worker 不可达时返回空上下文（`emptyResult`），绝不阻塞开场。

### ③ `observation`（← `PostToolUse`：你每次工具调用后，async）

- **入参**：`sessionId`、`toolName`、`toolInput`、`toolResponse`、`cwd`、`agentId/agentType`
- **门禁**：无 `toolName` 跳过；无 `cwd` 抛错；项目被排除跳过
- **主调用**：`POST /api/sessions/observations { contentSessionId, tool_name, tool_input, tool_response, cwd, ... }`
- **出参**：`{ continue: true, suppressOutput: true }`（纯写入，不回注任何上下文）

> 作用：**主线写入半环的接口端**——把你的每次工具调用「原样」丢给 worker，压缩成 observation 是 worker 的事（第五层）。注意它只是「投递」，不等结果。

### ④ `summarize`（← `Stop`：会话/回合结束时，async）

- **入参**：`sessionId`、`transcriptPath`、`lastAssistantMessage`、`stopHookActive`、`agentId`
- **门禁**：项目排除 / `stopHookActive`（防 Stop 重入）/ 子代理(`agentId`)上下文 → 跳过
- **取数**：优先用 `lastAssistantMessage`；否则从 `transcriptPath` 用 `extractLastMessage` 抽最后一条助手消息，并 `stripMemoryTags` 去掉记忆标签
- **主调用**：`POST /api/sessions/summarize { contentSessionId, last_assistant_message, ... }`（入队，worker 异步生成）
- **出参**：`{ continue: true, suppressOutput: true }`

> 作用：会话结束时**触发摘要生成**，产物落到 `session_summaries` 表。同样只是「入队」，生成是 worker 的活。

### ⑤ `file-context`（← `PreToolUse:Read`：你读文件前，async）

这是最「聪明」的一个，专为「读老文件时补上它的历史」设计。

- **入参**：`toolInput.file_path` / `filePaths`、`cwd`
- **多重门禁**（省 token 的关键）：
  - 文件 < `1500` 字节 → 跳过（小文件不值得补历史）
  - 文件 `mtime` 比最新 observation 还新 → 跳过（文件已变，旧记忆过时）
- **主调用**：`GET /api/observations/by-file?path=<绝对>&path=<相对>&projects=...` （同时发绝对/相对两种路径，兼容存储侧不同格式，见 #2691）
- **加工**：按会话去重 + 打分（改过该文件、涉及文件少的优先）→ 取前 15 条 → 按天分组，排版成一张文件时间线
- **出参**：
  ```ts
  { hookSpecificOutput: { hookEventName: 'PreToolUse', additionalContext: <时间线>, permissionDecision: 'allow' } }
  ```

> 作用：**你还没读完文件，Claude 就已经知道「这个文件过去被谁改过、为什么」**。注意它返回 `permissionDecision: 'allow'`——PreToolUse 输出必须表态放行。

### ⑥ `file-edit`（备用写入通道，非 claude-code 触发）

- **入参**：`filePath`、`edits`、`sessionId`、`cwd`
- **主调用**：`POST /api/sessions/observations { tool_name: 'write_file', tool_input: { filePath, edits }, tool_response: { success: true }, ... }`
- **出参**：`{ continue: true, suppressOutput: true }`

> 作用：给「编辑事件里不带 tool_response」的平台用的写入通道——把编辑动作也变成一条 observation。和 `observation` 殊途同归（都打 `/api/sessions/observations`）。

### ⑦ `user-message`（生成那条「Claude-Mem Context Loaded」横幅）

- **入参**：`cwd`、`platform`
- **主调用**：`GET /api/context/inject?project=<项目>` → 拿上下文
- **出参**：把上下文包成一条带 emoji 的横幅（含 `<private>` 用法提示、Discord 链接、`http://localhost:<port>/` 观看链接），通过 `systemMessage` 返回给用户

> 作用：**给用户看的欢迎/上下文横幅**（USER_HINT）。注意它用 `systemMessage` 而非 `additionalContext`——是给人看的，不进模型上下文。

## 贯穿七个 handler 的五条统一约定

读完你会发现它们「长得都一样」，因为共享同一套接口层约定：

1. **纯函数**：只返回 `HookResult`，绝不自己 print/exit（IO 纪律）。
2. **worker 降级**：一律用 `executeWithWorkerFallback` + `isWorkerFallback`——worker 不可达就返回「放行、空上下文」，从不阻塞你。
3. **项目门禁**：几乎都先过 `shouldTrackProject(cwd)`，被排除的项目直接跳过。
4. **双运行时**：写入类 handler 都有 `resolveRuntimeContext()` 分支——`runtime === 'server'` 走云端 API（cloud-sync，第八层），失败再 fall back 到本地 worker HTTP。**这是 cloud 与 local 的接入点。**
5. **两条输出通道**：`additionalContext` → 喂模型；`systemMessage` → 给用户。分得很清。

## 本层结束自测（对照「结束标准」）

> **结束标准**：能回答「Claude Code 每发生一件事，claude-mem 的哪段代码被执行？入参出参是什么？」

1. **我发了一条消息，执行了什么？** → `UserPromptSubmit` hook → `worker-service.cjs hook claude-code session-init` → `hookCommand` 归一化输入 → `sessionInitHandler` → `POST /api/sessions/init`；出参可能带 `additionalContext`（语义注入）。
2. **我读了个大文件，执行了什么？** → `PreToolUse:Read` → `file-context` handler → `GET /api/observations/by-file` → 返回该文件的历史时间线作为 `additionalContext`，并 `permissionDecision:'allow'`。
3. **worker 没起来会怎样？** → handler 里 `isWorkerFallback` 命中 → 返回 `continue:true`、空上下文；`hookCommand` 退出 0，不打断我。
4. **注入模型的上下文和终端里的提示，代码上有区别吗？** → 有：`hookSpecificOutput.additionalContext` 给模型，`systemMessage` 给用户，两条通道。

四题能答上来，就打通了「使用 ↔ 原理」的交界。下一层 **第四层** 我们跟着这些 handler 打过去的 worker 端点，进到 worker 里，先看它读写的**数据形状**（`observations` 表 / schemas）——链条流的到底是什么。
