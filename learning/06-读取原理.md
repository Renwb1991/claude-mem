# 第六层 · 懂读取原理（记忆是怎么「找回并注入」的）

> **目标**：主线的后半段——从检索到上下文注入。
> **方法**：跟着「一次新会话开场」走一遍，看记忆怎么被查出来、拼成一段文字、送回模型。
> **承接**：第五层把记忆写进了 `observations` / `session_summaries` 表和 Chroma 向量库。这一章回答**它们怎么被取回、组装、注入**——「下次会话开头那段上下文」就在这里生产。

---

## 开篇：三条读取路径，别混为一谈

读取比写入更容易混，因为**有三条并存的读路径，检索逻辑各不相同**。先把它们分开：

| 读路径 | 触发点 | 检索方式 | 产物 |
|---|---|---|---|
| **A. 会话开场自动注入** | `SessionStart` → `context` handler → `/api/context/inject` | **按项目 + 类型/概念过滤 + 时间倒序**（非语义！） | 「会话开头那段上下文」 |
| **B. 提问语义注入** | `UserPromptSubmit` → `session-init` → `/api/context/semantic` | 语义检索（按当前 prompt） | 追加的相关记忆 |
| **C. 主动检索** | Claude 调 MCP 工具 `search`/`timeline`/`get_observations` | 混合检索（Chroma 语义 + SQLite FTS） | 检索结果索引/详情 |

- **步骤 18（ContextBuilder）主要是路径 A**：注意它**不是语义检索**，而是「最近的、符合类型/概念的观察」。这颠覆很多人的直觉——**开场注入靠的是「近期 + 过滤」，不是「相关性排序」**。
- **步骤 17（SearchManager）主要是路径 C**：真正的混合语义检索在这里。
- 路径 B 是 A 和 C 之间的一个语义变体（第三层已见 `session-init` 里的 semanticInject 分支）。

想清楚「哪条路径用什么检索」，这一章就不会乱。

## 17. 检索逻辑（含向量检索）—— `SearchManager` + `search/`

### 17.1 分层：Facade → Orchestrator → Strategy

检索代码是干净的三层：

```
SearchManager（门面，1000+ 行）
   实现「3 层工作流」的对外方法：search / timeline / get_observations / getRecentContext
        │ 委托
        ▼
SearchOrchestrator（编排：选策略 + 降级）
        │ 委托
        ▼
  三个 Strategy：
    SQLiteSearchStrategy   —— FTS5 全文（第四层的 memory_items_fts / 旧库 observations_fts）
    ChromaSearchStrategy   —— 向量语义
    HybridSearchStrategy   —— 二者交集 + 排序（findByFile 用）
```

### 17.2 Orchestrator 的选择与降级逻辑（`SearchOrchestrator.executeWithFallback`）

这段逻辑是检索的「大脑」，值得记住：

```
if 没有 query（纯过滤查询）        → 直接走 SQLite（过滤不需要语义）
else if 配了 Chroma               → 走 Chroma 语义检索
        if 平台限定且结果为空       → 回退 SQLite（宁可给结果也别空手）
   catch Chroma 失败              → 抛 ChromaUnavailableError
else（没配 Chroma）               → 返回空 + strategy:'sqlite'
```

**核心取舍**：Chroma（语义）是优先项，但**处处有 SQLite 兜底**——和第五层「Chroma 失败仅告警」一脉相承：**向量检索是增强，关键词/过滤是保底，向量层挂了系统仍可用。**

### 17.3 向量检索的关键套路：Chroma 存索引，SQLite 存真身（hydrate）

看 `ChromaSearchStrategy.search`：

```
query 文本 → chromaSync.queryChroma(...) → 返回一批命中的 metadata（含 sqlite_id）
          → 从 metadata 取出 sqlite_id 列表
          → sessionStore.getObservationsByIds(ids)   ← 回 SQLite 取「完整内容」
```

**Chroma 里只存向量 + 轻量 metadata（`sqlite_id`/`doc_type`/`project`/`title`…，见 `search/types.ts` 的 `ChromaMetadata`），不存正文。** 命中后拿 `sqlite_id` 回 SQLite「注水（hydrate）」成完整记录。这是向量库 + 关系库配合的经典模式：**向量库负责「找到哪条」，SQLite 负责「这条是什么」。**

`HybridSearchStrategy.findByFile`（第三层 `file-context` 用的 by-file 查询背后）更进一步：先用 SQLite 按文件筛出候选 id，再用 Chroma 语义排序，`intersectWithRanking` 取交集并保留 Chroma 的相关性顺序——**过滤靠 SQLite，排序靠 Chroma。**

### 17.4 SearchManager 落实「3 层工作流」

第一层用 `mem-search` 技能时见过的省 token 工作流，实现就在 `SearchManager`：

| 方法 | 对应工作流层 | 产出 | token 量 |
|---|---|---|---|
| `search` | ① 索引 | 一张带 ID/时间/类型/标题的紧凑表 + 每条的 token 估算（`estimateTokens`） | ~50-100/条 |
| `timeline` | ② 上下文 | 围绕某 anchor（ID 或 query 命中）前后 N 条记录 | 中 |
| `get_observations`（→ `getObservationsByIds`） | ③ 详情 | 仅指定 ID 的完整正文 | ~500-1000/条 |

`timeline` 有三种锚定模式：query 命中最高分作锚、显式 anchor ID、时间戳锚（`getTimelineAroundObservation` / `getTimelineAroundTimestamp`）。**「先给便宜索引，再按需拉详情」——省 token ≈10×，这就是渐进式披露落到检索层的样子。**

> ✅ **本步小结**：SearchManager（门面/3层工作流）→ Orchestrator（选策略+降级）→ Strategy（SQLite FTS / Chroma 语义 / Hybrid）。向量检索 = Chroma 找 `sqlite_id`、SQLite 注水取正文。Chroma 处处有 SQLite 兜底。

## 18. ⭐ 上下文组装与 token 预算 —— `src/services/context/`

这是路径 A 的实现，也是「会话开头那段上下文」的**唯一生产者**。入口 `generateContext(input)`（`ContextBuilder.ts`）。

### 18.1 组装流水线（`generateContextWithStats`）

```
loadContextConfig()                 ← ① 读配置：数量/类型/概念/开关（settings + mode）
  ↓
queryObservationsMulti(db, ...)     ← ② 查观察：按项目+类型+概念过滤，时间倒序，LIMIT
querySummariesMulti(db, ...)        ←    查摘要：按项目，时间倒序
  ↓ 空？ → renderEmptyState 返回
buildContextOutput():
  calculateTokenEconomics()         ← ③ 算 token 账
  renderHeader → renderTimeline → renderSummaryFields → renderPreviouslySection → renderFooter
  ↓
返回 { text, stats }                 ← text = 注入的上下文；stats = 遥测
```

### 18.2 关键认知①：注入检索是「近期 + 过滤」，不是语义

`queryObservationsMulti` 的 SQL（`ObservationCompiler.ts`）说明一切：

```sql
FROM observations o LEFT JOIN sdk_sessions s ...
WHERE (o.project IN (...) OR o.merged_into_project IN (...))   -- 按项目（含合并项目）
  AND (platformSource 匹配)                                     -- 按平台
  AND type IN (...)                                             -- 按 mode 允许的类型
  AND EXISTS (json_each(o.concepts) WHERE value IN (...))       -- 至少含一个目标概念
ORDER BY o.created_at_epoch DESC                                -- 时间倒序
LIMIT totalObservationCount                                     -- 数量上限
```

**没有相似度、没有 query。** 开场注入的逻辑是：「这个项目里，最近的、类型和概念符合的观察，取前 N 条」。类型/概念白名单来自当前 mode（`loadContextConfig` 从 `mode.observation_types/observation_concepts` 取）——**又是第一层 `CLAUDE_MEM_MODE` 的落点。**

> 💡 为什么这样设计？开场时还没有用户 query，"最近做了什么"比"跟某句话最相关"更有用。真正的语义匹配交给路径 B（有 prompt 时）和路径 C（用户主动搜）。

### 18.3 关键认知②：token 预算 = 「读取成本 vs 发现成本」的账（`TokenCalculator.ts`）

这是 claude-mem 的核心价值主张，被量化成 `TokenEconomics`：

```
readTokens      = 读这条压缩记忆要花的 token（≈ 标题+副标题+叙述+facts 的字符数 / 4）
discoveryTokens = 当初「发现」这条信息花掉的 token（写入时记录，见第五层 discovery_tokens）
savings         = discoveryTokens - readTokens        ← 省了多少
savingsPercent  = savings / discoveryTokens
```

含义：**当初 Claude 花了几千 token 读文件/跑命令才搞懂的事，现在读一条几十 token 的记忆就能复得——差值就是记忆系统省下的钱。** 第一层 Web UI 和 header/footer 里显示的「tokens saved」就来自这里。`CHARS_PER_TOKEN_ESTIMATE = 4` 是那个粗略换算。

> 注意这是**估算**（字符数 /4），不是精确计费——用于展示价值，不用于结算。

### 18.4 关键认知③：渐进式披露落到「组装」层

- `config.totalObservationCount`：进 timeline 的观察总数。
- `config.fullObservationCount`：其中前几条给「完整」正文，其余只给紧凑行（`getFullObservationIds` 圈出这批 ID）。
- `input.full === true` 时把两个上限都设成 999999（`/learn-codebase` 或全量预览用）。

于是注入的上下文是**分层的**：最近几条展开细节，更早的只留标题时间线——**在有限 token 里最大化信息密度。**

### 18.5 sections/ 与 formatters/：把数据渲染成文字

- **`sections/`**：`HeaderRenderer`（项目名 + token 经济）、`TimelineRenderer`（按天分组的观察/摘要时间线，含 full/紧凑之分）、`SummaryRenderer`（最近一条会话摘要的 request/investigated/learned…）、`FooterRenderer`（"Previously" 上次会话最后一句 + 收尾）。
- **`formatters/`**：`AgentFormatter` vs `HumanFormatter`——`forHuman` 开关决定给「模型吃的纯文本」还是「人看的带颜色终端输出」。第三层 `context` handler 里 `colors=true`（claude-code）走的就是 human 版拼进 `systemMessage`。
- **"Previously" 段**（`getPriorSessionMessages` + `extractPriorMessages`）：从上一个会话的 `.jsonl` 转录里抠出最后一句助手消息，让新会话「接得上话」。这里有个 `cwdToDashed` 的坑注释（#2401：路径里的 `.` 也要转 `-`，否则带点用户名如 `john.doe` 会失效），是很真实的工程细节。

> ✅ **本步小结**：`generateContext` = 读配置 → 按「项目+类型+概念+近期」查观察/摘要（**非语义**）→ 算 token 经济账（发现成本 - 读取成本 = 节省）→ 分层渲染（full/紧凑）→ Agent/Human 两种格式。产物就是注入的上下文。

## 19. 以 MCP 工具形式对外暴露检索 —— `src/servers/mcp-server.ts` + `src/server/mcp/recall-mcp-server.ts`

路径 C（Claude 主动检索）通过 MCP 工具暴露。有**两个 MCP server**，对应本地与云端。

### 19.1 `mcp-server.ts` —— 本地 stdio MCP（Claude Code 用的那个）

这是第二层里那个「独立进程 `mcp-server.cjs`」的源头。它注册一批工具，**大多只是转发到 worker 的 HTTP 接口**（`callWorker('/api/search', ...)` 等），真正干活的还是 worker 里的 SearchManager。

工具家族（`inputSchema` 定义参数）：

| 工具 | 作用 | 归属 |
|---|---|---|
| `search` / `timeline` / `get_observations` | **3 层工作流**（proxy 到 `/api/search`、`/api/timeline`） | 核心记忆检索 |
| `session_start_context` | 拉会话开场上下文（第三层 Codex 平台的 `context` 走它） | 注入 |
| `smart_search` / `smart_outline` / `smart_unfold` | 用 tree-sitter 结构化搜代码 | 代码探索 |
| `build_corpus` / `list_corpora` / `prime_corpus` | 知识 corpus | 第八层 knowledge-agent |
| `observation_*` | 仅 server runtime（云端）可用 | cloud |

顶部还塞了个 `__IMPORTANT` 工具，内容就是「先 search 拿索引 → timeline 看上下文 → get_observations 拉详情」的用法说明——**把省 token 工作流直接写进工具清单教模型怎么用。**

### 19.2 `recall-mcp-server.ts` —— 云端只读 recall MCP

这是给「粘贴一个托管 recall 链接」或 Server Beta 用的**只读**检索面。工厂函数 `createRecallMcpServer(backend, version)`：

- 只暴露三个读工具：`search`、`context`（= search + 拼好可注入的 context 串）、`recent`。
- **刻意不含任何写工具**——「粘来的 recall 链接是只读的」（注释明说）。
- 通过注入的 `RecallBackend` 访问存储，且**按 API key 的 team/project 权限作用域**（多租户隔离）。它查的是云端 Postgres（`/v1/search`、`/v1/context`），和本地 stdio server 查 SQLite 是「同一套 recall 语义、两套后端」——正好呼应第四层「一套 schema 两个后端」。

> ✅ **本步小结**：两个 MCP server——本地 stdio（proxy 到 worker/SearchManager，含 3 层工作流 + 代码探索 + corpus）与云端只读 recall（team 作用域、无写工具）。它们把「检索能力」以工具形式交给模型主动调用。

## 回到主线：读取半环完整走一遍（路径 A）

```
下次在同项目开新会话
 → SessionStart hook → context handler（第三层）
 → GET /api/context/inject?projects=...
 → generateContext():
      loadContextConfig（类型/概念白名单来自 mode）
      queryObservationsMulti：项目内 + 类型/概念过滤 + 时间倒序 + LIMIT   ← 非语义！
      querySummariesMulti
      calculateTokenEconomics（省了多少 token）
      buildTimeline + 分层渲染（前 N 条 full，其余紧凑）
      renderPreviouslySection（上次会话最后一句）
 → 返回一段文字
 → context handler 包成 hookSpecificOutput.additionalContext
 → 注入到新会话开头 → Claude 一开场就"记得"上次
```

**主线问题彻底闭合了**：你编辑的那个文件 → 第五层压成 observation 落库 → 这一层在下次开场时，作为「近期同项目、类型符合」的一条，被查出、算好 token 账、渲染进时间线、注入回会话开头那段上下文。

## 本层结束自测

1. **会话开场注入用的是语义检索吗？** → **不是**。`queryObservationsMulti` 按「项目 + 类型/概念白名单 + 时间倒序 + LIMIT」取近期观察，无相似度。语义检索是另两条路径（提问注入 / 主动 MCP 搜索）。
2. **向量检索命中后，正文从哪来？** → Chroma 只存向量 + `sqlite_id` 等 metadata；拿 `sqlite_id` 回 SQLite `getObservationsByIds` 注水（hydrate）取正文。
3. **Chroma 挂了会怎样？** → 检索层处处有 SQLite/FTS 兜底（Orchestrator 降级），关键词与过滤仍可用；向量只是增强。
4. **"节省的 token" 是怎么算的？** → `discovery_tokens`（当初发现该信息花的）− `readTokens`（读这条压缩记忆花的），差值即节省，估算按字符数/4。
5. **3 层工作流（search→timeline→get_observations）省 token 的原理？** → search 只回紧凑索引（~50-100/条）让模型筛，再对选中的 ID 才拉完整正文（~500-1000/条），避免一次性拉全量。
6. **两个 MCP server 有何分工？** → 本地 stdio（`mcp-server.ts`，proxy 到 worker，含全部工具）；云端只读 recall（`recall-mcp-server.ts`，team 作用域、仅 search/context/recent、无写工具）。

六题能答上来，主线的「写入→读取」闭环就整个通了。接下来 **第七层** 抬升视角：看那个把写入、读取、存储、检索全都串起来的常驻 worker 是怎么编排的。
