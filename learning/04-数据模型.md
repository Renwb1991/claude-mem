# 第四层 · 懂数据模型（原理的地基：先看「记忆长什么样」）

> **目标**：在读读写逻辑之前，先固定住数据结构，否则后面会飘。
> **方法**：只看「形状」和「怎么落库」，不看压缩/检索逻辑（那是五、六层）。
> **承接**：第三层的 handler 把数据打到 worker 的 `/api/sessions/observations` 等端点。这一章回答——**打进去的东西，最终以什么结构、存在哪张表、怎么读回来。**

---

## 开篇必读：这个项目里有「两套」数据模型

这是最容易让人困惑的一点，先讲清楚，否则你会在「第一层看到的表」和「schema.ts 里定义的表」之间反复迷路。

| | **旧：worker 本地存储** | **新：统一 server 存储** |
|---|---|---|
| 定义位置 | `src/services/sqlite/SessionStore.ts` | `src/storage/`（本章主角） |
| 代表表 | `observations`、`session_summaries`、`user_prompts`、`sdk_sessions` | `memory_items`、`memory_sources`、`projects`、`server_sessions`、`agent_events` |
| 你在哪见过 | **第一层 `claude-mem.db` 里就是它**（当前本地主力存储） | cloud-sync / server runtime 用 |
| 特点 | 每种记忆一张表（observation/summary/prompt 分开） | **一张 `memory_items` 用 `kind` 区分**，更规范 |
| 后端 | 只有 SQLite | SQLite（本地）+ Postgres（云端），**同一套 schema** |

**它们怎么连起来？** 新模型的 `memory_items.legacy_observation_id` 和 `memory_sources`（来源溯源表）就是桥——把旧的 `observations.id` 映射到新的 `memory_items`。

> 📌 本章讲的是**新的统一模型**（步骤 11-13 指定的 `src/core/schemas/` + `src/storage/`），因为它是项目演进的方向，也是「一套 schema、两个后端」这个核心抽象的所在。凡涉及旧模型处会显式标注。

## 11. ⭐ 记忆的核心数据结构 —— `src/core/schemas/`

### 11.1 关键认知：Zod schema 是「唯一真相源」

`src/core/schemas/` 下每个文件都用 [Zod](https://zod.dev) 定义数据形状。这不是普通的 TS interface，而是**运行时可校验的 schema**，一份定义同时产出两样东西：

```ts
export const MemoryItemSchema = z.object({ ... });         // ① 运行时校验器
export type MemoryItem = z.infer<typeof MemoryItemSchema>; // ② 编译期 TS 类型
```

于是数据进出存储层时都能 `Schema.parse(row)` 做一次运行时校验——**坏数据在边界就被挡住**，而类型又能被 TS 静态检查。记住这个「schema = 校验器 + 类型」的双重身份，第 12 步到处是它。

### 11.2 `MemoryItem` —— 统一的记忆记录（最核心）

`memory-item.ts`。这是整个新模型的中心，**所有种类的记忆都是一条 MemoryItem**，靠 `kind` 区分：

```ts
kind: z.enum(['observation', 'summary', 'prompt', 'manual'])   // 记忆的种类
type: z.string()          // 更细的分类，如 bugfix/feature/decision/discovery/change
title / subtitle          // 标题
text / narrative          // 正文 / 叙述
facts:    z.array(z.string())   // 事实列表
concepts: z.array(z.string())   // 概念列表
filesRead / filesModified: z.array(z.string())  // 读过/改过的文件
metadata: z.record(...)   // 自由扩展
projectId / serverSessionId     // 归属：哪个项目、哪次会话
legacyObservationId       // 桥：对应旧 observations.id
createdAtEpoch / updatedAtEpoch // 时间戳（epoch 毫秒整数）
```

> 💡 对照第一层：你在旧 `observations` 表看到的 `title/type/narrative/facts/files_read...` 字段，在新模型里**原封不动搬进了 `memory_items`**，只是多了个 `kind` 把 observation / summary / prompt 三类合并进同一张表。**记忆的「形状」没变，收纳方式变规范了。**

同文件还有 **`MemorySource`（来源溯源）**：记录一条 memory 是从哪来的（`sourceType ∈ observation/session_summary/user_prompt/manual/import`），并通过 `legacyTable` + `legacyId` 指回旧表。**它是「旧数据迁移进新模型」的关键账本。**

### 11.3 `Create*` 变体：写入用的「瘦身版」schema

每个 schema 都配一个 `CreateXxxSchema`，规律一致：

```ts
export const CreateMemoryItemSchema = MemoryItemSchema
  .omit({ id: true, createdAtEpoch: true, updatedAtEpoch: true })  // 去掉「由系统生成」的字段
  .partial({ title: true, subtitle: true, ... });                 // 其余可选字段允许缺省
```

含义：**创建时你不该、也不能提供 `id` 和时间戳**（由仓库生成），可选字段可以不传。读时用完整 `Schema`，写时用 `CreateSchema`——这个「读全/写瘦」的配对贯穿所有仓库。

### 11.4 其余四个 schema（快速过）

| 文件 | schema | 是什么 | 关键字段 |
|---|---|---|---|
| `session.ts` | `ServerSession` | 一次会话的元数据 | `status ∈ active/completed/failed`、`contentSessionId`、`memorySessionId` |
| `project.ts` | `Project` | 一个项目 | `name`、`slug`(唯一)、`rootPath`(唯一) |
| `agent-event.ts` | `AgentEvent` | 一条原始事件（未压缩） | `sourceType ∈ hook/worker/provider/server/api`、`eventType`、`payload` |
| `team.ts` / `auth.ts` | Team / ApiKey 等 | 多人协作与鉴权（云端） | —— |

> 数据流上的关系：`AgentEvent`（原始事件，如一次 tool_use）经压缩 → 变成 `MemoryItem`（记忆）；两者都挂在 `ServerSession` 下，会话又挂在 `Project` 下。这条「事件 → 记忆」的因果链，第五层会走一遍。

> ✅ **本步小结**：Zod schema = 校验器 + 类型。`MemoryItem` 是统一记忆记录（`kind` 区分种类），`MemorySource` 溯源，`ServerSession`/`Project`/`AgentEvent` 是它的上下文。`Create*` 变体用于写入。

## 12. 落库表结构与读写 —— `src/storage/sqlite/`

### 12.1 `schema.ts` —— 建表 DDL 与七条约定

`ensureServerStorageSchema(db)` 一次性建好所有表、索引、触发器。读它就是读「数据库长啥样」。归纳出**七条贯穿全库的约定**：

1. **主键是 TEXT UUID**：`id TEXT PRIMARY KEY`（`randomUUID()` 生成），不是自增整数——为了跨 SQLite/Postgres/多机同步不撞号。
2. **时间一律 epoch 整数**：`created_at_epoch INTEGER`，存 `Date.now()` 的毫秒数，无时区烦恼。
3. **数组/对象存成 JSON 文本**：`facts TEXT NOT NULL DEFAULT '[]'`、`metadata TEXT ... DEFAULT '{}'`——SQLite 没有原生数组，用 TEXT 存 JSON，读时再解析（见 serde）。
4. **枚举用 CHECK 约束**：`kind TEXT ... CHECK(kind IN ('observation','summary','prompt','manual'))`——和 Zod enum 双保险，数据库层也挡非法值。
5. **外键 + 级联**：`FOREIGN KEY(project_id) REFERENCES projects(id) ON DELETE CASCADE`——删项目自动清子记录；会话删除则 `SET NULL`。
6. **完整性触发器**：一组 `trg_*_session_project_*` 触发器强制「子记录（memory_items/agent_events）的 `server_session_id` 必须属于同一个 `project_id`」，违反直接 `RAISE(ABORT)`。**数据库自己守护跨项目一致性。**
7. **FTS5 全文索引 + 同步触发器**：`memory_items_fts` 是虚拟表（`tokenize='porter unicode61'`），三个触发器 `trg_memory_items_fts_{insert,update,delete}` 让它跟 `memory_items` 实时同步。这就是第六层「关键词检索」的底座（向量检索是另一套 Chroma）。

还有两个健壮性细节：
- **幂等**：用 `WeakSet` 记住已初始化的 db + `CREATE ... IF NOT EXISTS`，重复调用无副作用。
- **FTS 自愈**：启动时比对 `memory_items` 与 `memory_items_fts` 行数，不一致就重建索引。

> 版本号 `SERVER_STORAGE_SCHEMA_VERSION = 33` 记录 schema 演进代数。

### 12.2 仓库模式（Repository）—— 读写的唯一入口

`memory-items.ts` / `projects.ts` 等每个文件导出一个 `XxxRepository` 类。它们长得一模一样，是标准的 **Repository 模式**：

```ts
export class MemoryItemsRepository {
  constructor(private db: Database) {
    ensureServerStorageSchema(this.db);   // 构造即保证表存在
  }
  create(input: CreateMemoryItem): MemoryItem { ... }   // 写：Create* 校验 → INSERT
  getById(id): MemoryItem | null { ... }                // 读：SELECT → mapRow
  listByProject(projectId, limit): MemoryItem[] { ... }
  search(projectId, query, limit): MemoryItem[] { ... } // 走 FTS5
}
```

**贯穿每个方法的「双向翻译 + 双重校验」**，看 `create` 和 `mapMemoryItemRow` 就懂了：

```
写入：CreateMemoryItemSchema.parse(input)   ← ① Zod 校验入参
     → 生成 id=randomUUID()、时间=Date.now()
     → stringifyJson(facts/concepts/...)     ← ② camelCase 对象 → JSON 文本列
     → INSERT (snake_case 列)

读取：SELECT * → MemoryItemRow (snake_case)
     → parseJsonArray(row.facts) 等          ← ③ JSON 文本列 → 数组
     → MemoryItemSchema.parse({...})          ← ④ Zod 校验出参 + 转 camelCase
     → 返回 MemoryItem (domain 对象)
```

两个要点：
- **列名 snake_case ↔ 领域对象 camelCase**，翻译只发生在仓库里，外面永远见 camelCase。
- **进出都过 Zod**（写用 `Create*.parse`，读用 `Schema.parse`）——坏数据在仓库边界就抛错，业务层拿到的一定是合法结构。

### 12.3 `serde.ts` —— JSON 列的防御式(反)序列化

就三个小函数，但很重要：`stringifyJson`（写）、`parseJsonObject` / `parseJsonArray`（读）。关键在**读时容错**——解析失败不抛错，而是记一条 warn 并返回 `{}` / `[]`：

```ts
catch (error) { logger.warn('DB', 'Failed to parse ...'); return []; }
```

> 设计意图：单条记录的 JSON 列损坏，不该让整个查询崩掉。这和第三层「hook 优雅降级」是同一种健壮性哲学——**局部坏数据不拖垮全局。**

`index.ts` 只是把 `agent-events / auth / memory-items / projects / schema / server-sessions` 统一 re-export，是这层的门面。

> ✅ **本步小结**：`schema.ts` 定义表（七条约定：UUID主键 / epoch时间 / JSON文本列 / CHECK枚举 / 外键级联 / 完整性触发器 / FTS5同步）。Repository 是唯一读写入口，做 snake↔camel 翻译 + 进出 Zod 双校验。`serde.ts` 管 JSON 列的容错(反)序列化。

## 13. 对照第二套后端理解存储抽象 —— `src/storage/postgres/`

### 13.1 核心抽象：一套 schema，两个后端

这是本章最值得带走的架构洞见。`src/storage/` 下**并列两个后端实现**，共享 `src/core/schemas/` 同一套 Zod 定义：

```
              src/core/schemas/  (唯一真相源：MemoryItem / Project / ServerSession / ...)
                     │
        ┌────────────┴─────────────┐
        ▼                          ▼
 src/storage/sqlite/        src/storage/postgres/
 （本地 server runtime）      （云端 cloud-sync）
 MemoryItemsRepository       PostgresObservationRepository
 ProjectsRepository          PostgresProjectsRepository
 ...                         ...
```

对照 `postgres/index.ts`，它导出一个 `PostgresStorageRepositories` 接口，成员和 SQLite 侧**一一对应**（projects / sessions / agentEvents / observations / auth / teams…）。也就是说：

> **业务层只依赖「仓库接口」，不关心底下是 SQLite 还是 Postgres。** 本地用 SQLite、云端用 Postgres，切换后端不动业务代码——这就是「存储抽象」的价值。

### 13.2 两个后端的异同（诚实对照）

| 维度 | SQLite (`storage/sqlite`) | Postgres (`storage/postgres`) |
|---|---|---|
| 用途 | 本地 server runtime | 云端多租户 / cloud-sync |
| 建表 | `ensureServerStorageSchema`（同步、幂等、`IF NOT EXISTS`） | `bootstrapServerPostgresSchema`（异步、事务、迁移表记录版本） |
| 版本 | `SERVER_STORAGE_SCHEMA_VERSION = 33` | `SERVER_POSTGRES_SCHEMA_VERSION = 1` |
| 迁移 | 靠幂等 DDL | `server_beta_schema_migrations` 表 + `INSERT ... ON CONFLICT DO NOTHING` |
| JSON 列 | TEXT 存 JSON，手工 serde | 原生 `jsonb`（更强） |
| 记忆表命名 | `memory_items` / `memory_sources` | `observations` / `observation_sources` |
| 额外能力 | —— | 用量计费(`usage_events`)、限流(`rate_limit_counters`)、生成任务(`observation_generation_jobs`) |

⚠️ **注意那处命名分歧**：SQLite 侧叫 `memory_items`，Postgres 侧仍叫 `observations`——源码注释说明这是 `cmem-sdk rename` 迁移进行中、Postgres 的表名是已持久化的 DDL 标识符暂未改。**读代码时别被两个名字绕晕，它们承载的是同一个 `MemoryItem` 形状。**

### 13.3 Postgres 侧多出来的东西 = 云端才需要的能力

`SERVER_POSTGRES_TABLES` 比 SQLite 多了 `usage_events`（计费）、`rate_limit_counters`（限流）、`observation_generation_jobs`（异步生成任务队列）——这些是**多租户云服务**才需要、本地单机用不上的。这解释了「为什么云端后端更复杂」。

> ✅ **本步小结**：`src/storage/` = 一套 core schema + 两个后端实现（SQLite 本地 / Postgres 云端），仓库接口一一对应，业务层与后端解耦。差异集中在「建表/迁移方式、JSON 列类型、云端专属表（计费/限流/任务）」，以及一处 `memory_items` vs `observations` 的历史命名分歧。

## 回到主线：链条里流动的到底是什么？

把这一章挂回主线问题：

```
你编辑文件 →(observation handler) POST /api/sessions/observations
   → worker 收到「原始事件」            = AgentEvent 形状（payload 里是 tool_use）
   → 压缩（第五层）                      = 生成一条 MemoryItem（kind='observation'）
   → 落库                               = memory_items 表（或旧 observations 表）
   → 下次检索（第六层）                  = 从 memory_items / FTS5 / Chroma 读回 MemoryItem
```

**这一章让你认得链条里流动的两种「货物」**：进 worker 的是 `AgentEvent`（原始、未压缩），出来存下的是 `MemoryItem`（提炼后的记忆）。后面五、六层就是这两者之间的「加工」与「取回」。

## 本层结束自测

1. **一条 observation 记忆，在新模型里存哪张表、怎么和 summary 区分？** → 存 `memory_items`，靠 `kind` 字段（`observation`/`summary`/`prompt`/`manual`）区分；旧模型里它们是三张分开的表。
2. **`facts` 是个字符串数组，SQLite 里怎么存的？** → 存成 JSON 文本列（`TEXT DEFAULT '[]'`），写时 `stringifyJson`、读时 `parseJsonArray`，解析失败返回空数组不崩。
3. **为什么读写都要过 `Schema.parse`？** → Zod 在存储边界做运行时校验，坏数据当场抛错；同时 `z.infer` 提供静态类型。校验器 + 类型一份定义。
4. **SQLite 和 Postgres 两套代码，业务层怎么不用改就能切换？** → 都实现同一套 `src/core/schemas/` 定义的形状，仓库接口一一对应，业务只依赖接口不依赖后端。
5. **第一层我在 `claude-mem.db` 看到的是 `observations` 表，可这章讲 `memory_items`？** → 那是旧的 worker 本地存储（`SessionStore.ts`，当前本地主力）；本章的 `memory_items` 是新的统一 server 存储，两者靠 `legacy_observation_id` / `memory_sources` 桥接。

五题能答上来，数据地基就稳了。下一层 **第五层** 正式进入写入原理——看 `AgentEvent` 是如何被 transcripts 读出、被 sdk 压缩成 `MemoryItem` 的。
