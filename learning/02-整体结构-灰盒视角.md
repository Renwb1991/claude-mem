## 5. ⭐ 运行时全景：常驻 worker、端口、请求流、路由分层

> 材料：`src/services/worker/README.md`（这一章把它从「功能清单」升级为「架构图」）

### 5.1 系统里到底有哪些「进程」

这是整个系统最重要的一张图。claude-mem 不是「一个程序」，而是**几个进程协作**：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Claude Code 主进程                            │
│  你在这里写代码。每到关键时刻，它按 hooks.json 触发一个 hook       │
└───────────────┬───────────────────────────────┬─────────────────┘
                │ (1) 触发 hook                   │ (2) Claude 需要检索记忆
                │  运行一个「薄壳」shell 命令       │  调用 MCP 工具
                ▼                                 ▼
   ┌────────────────────────┐        ┌──────────────────────────┐
   │  hook shell 脚本        │        │  MCP 服务器（独立进程）   │
   │  （bun-runner.js →      │        │  mcp-server.cjs           │
   │   worker-service.cjs）  │        │  stdio 协议，见 .mcp.json │
   └───────────┬────────────┘        └────────────┬─────────────┘
               │ HTTP 请求                          │ HTTP 请求
               │ (127.0.0.1:<port>)                 │
               ▼                                    ▼
   ┌───────────────────────────────────────────────────────────────┐
   │           常驻 Worker 服务（后台「大脑」，Bun 管理）           │
   │           worker-service.cjs · 一个本地 HTTP Server            │
   │                                                               │
   │   路由层 → 服务层 → { SQLite  ·  Chroma向量库  ·  搜索逻辑 }   │
   └───────────────────┬───────────────────────┬───────────────────┘
                       │                        │
                       ▼                        ▼ (压缩时调用，唯一出网)
             ~/.claude-mem/claude-mem.db   AI Provider API
             + ~/.claude-mem/chroma/       (Claude / Gemini / OpenRouter)
```

**关键认知（记住这 4 点）**：

1. **hook 是「薄壳」，不是干活的人**。Claude Code 每次触发的 hook 只是一小段 shell，作用是「找到插件、用 bun 起一个短命进程、向 worker 发一个 HTTP 请求」，然后立刻退出。真正干活的是 worker。
2. **worker 是唯一的常驻进程**，是所有能力的中枢：压缩、存储、检索、Web UI 全在它里面。第一层看到的 `worker.pid` 就是它。
3. **MCP 服务器是另一个独立进程**（`mcp-server.cjs`，走 stdio），是 Claude「主动检索记忆」的入口。它本身也只是转发到 worker 的 HTTP 接口。
4. **一切通信都收敛到 worker 的本地 HTTP**。不管是 hook 还是 MCP，最后都变成对 `127.0.0.1:<port>` 的请求。

> 💡 一句话：**hook 和 MCP 是两个「入口」，worker 是唯一的「引擎」，SQLite + Chroma 是「仓库」。**

### 5.2 端口是怎么定的（复习 + 定性）

worker 监听的端口规则（全系统统一）：

```
CLAUDE_MEM_WORKER_PORT 环境变量
  → 否则 settings.json 里的同名配置
  → 否则默认 37700 + (uid % 100)
host 默认 127.0.0.1（可被 CLAUDE_MEM_WORKER_HOST 覆盖）
```

本机实测是 `37702`（第一层从 `worker.pid` 看到的）。**按 uid 取模**是为了让多账号/多用户在同机上各用各的端口，不打架。

### 5.3 请求流：一个请求进 worker 后怎么走

`src/services/worker/README.md` 给的官方请求流，就是 worker 内部的分层：

```
Hook 或 MCP 客户端
  → HTTP 请求到 worker
    → 路由处理器（src/services/worker/http/routes/）
      → 服务层 → SQLite / Chroma / 搜索逻辑
```

**worker 的路由是按「领域」分类的**（每个是一个 Route 类，第七层才进去读实现）：

| 路由类 | 管什么 | 对应第一层现象 |
|---|---|---|
| `ViewerRoutes` | `GET /`、`/stream`（SSE） | Web UI + 实时推送 |
| `DataRoutes` | `/api/observations`、`/summaries`、`/prompts` | 存储的数据列表 |
| `SearchRoutes` | `/api/search`、`/api/timeline` | mem-search 背后 |
| `SettingsRoutes` | `/api/settings`、依赖健康 | 配置页 |
| `CorpusRoutes` | `/api/corpus/*` | knowledge-agent 语料 |
| `SessionRoutes` / `MemoryRoutes` / `LogsRoutes` / `ChromaRoutes` | 会话 / 记忆 / 日志 / Chroma 状态 | —— |

> ✅ **本步小结**：三类进程（hook 薄壳、MCP 服务器、常驻 worker）+ 两个仓库（SQLite、Chroma）+ 一次出网（Provider）。所有入口最终都打到 worker 的本地 HTTP，worker 内部按「路由→服务→存储」三层处理。

## 6. 目录三段式：源码 → 构建 → 安装

> 材料：`CLAUDE.md` + `package.json` 的 `scripts`

理解这一段，你才知道「我改了 `src/` 里的代码，为什么 Claude Code 里没生效」——因为中间隔着**构建**和**同步**两步。

### 6.1 三个目录，三种身份

| 阶段 | 位置 | 身份 | 谁在这里 |
|---|---|---|---|
| ① 源码 | `<repo>/src/` | 你写的 TypeScript | 开发者编辑的地方 |
| ② 构建产物 | `<repo>/plugin/` | 打包好的可运行插件 | `plugin/scripts/*.cjs`、`hooks/`、`skills/`、`modes/` |
| ③ 安装位置 | `~/.claude/plugins/marketplaces/thedotmack/` | Claude Code 实际加载的插件 | 从 repo 同步过去的一份拷贝 |

> 关键：**Claude Code 运行的是 ③，不是你编辑的 ①。** 中间靠构建（①→②）和同步（②→③）打通。

### 6.2 一条命令打通全链：`npm run build-and-sync`

`CLAUDE.md` 让你日常只记这一条。拆开看它做了什么（全在 `package.json` scripts 里）：

```
npm run build-and-sync
├─ npm run build                              # ① → ②：源码构建成插件产物
│   ├─ node scripts/sync-plugin-manifests.js  #   同步各处 manifest（版本号/命令声明）
│   ├─ node scripts/build-hooks.js            #   构建 hook 脚本
│   └─ node scripts/gen-plugin-lockfile.cjs   #   生成插件 lockfile
├─ npm run sync-marketplace                   # ② → ③：把 plugin/ 同步到已安装的 marketplace 目录
└─ (cd ~/.claude/.../thedotmack && worker:restart)  # 重启 worker，让新代码生效
```

**最后那步「重启 worker」是关键**：因为 worker 是常驻进程，不重启它，改的代码不会被加载。这解释了「为什么我改完要 `build-and-sync` 而不是直接生效」。

### 6.3 其余 scripts 快速归类（知道有就行）

`package.json` 里几十个 script，按用途归类，心里有数即可：

| 类别 | 代表 script | 干嘛 |
|---|---|---|
| worker 管理 | `worker:start/stop/restart/status`、`worker:logs` | 手动控制后台大脑 |
| 构建 | `build`、`build:binaries`、`build:cli-binary` | 打包 |
| 测试 | `test`、`test:sqlite`、`test:search`、`test:context` | 分模块跑测试（第八层用） |
| 类型检查 | `typecheck` | tsc --noEmit |
| 队列 | `queue`、`queue:process` | 处理 pending 消息队列 |
| 翻译 | `translate:tier1..4` | README 多语言 |
| 发布 | `release:patch/minor/major` | 版本发布（changelog 自动生成，勿手改） |
| Cursor 集成 | `cursor:install/status` | 跨编辑器 |

> ✅ **本步小结**：`src/`（写）→ `plugin/`（构建产物）→ marketplace 目录（Claude Code 实际加载）。日常改完记一条 `npm run build-and-sync`，它含「构建 + 同步 + 重启 worker」三步，最后一步重启是让常驻 worker 加载新代码的必要动作。

## 7. ⭐ 主数据流：把现象串成「写入 → 读取」闭环

> 这是**贯穿全书的主线**。第一层看到的每个现象，都是这条链上的一个点。

### 7.1 真实的 hook → 动作映射（来自 `plugin/hooks/hooks.json`）

先把「Claude Code 每发生一件事，触发谁」这张真值表钉死（**这是实测解析出来的，不是猜的**）：

| hook 事件 | 触发时机 | 调用的子命令 | 属于 |
|---|---|---|---|
| `Setup` | 插件初始化 | `version-check` | 装配 |
| `SessionStart` | 会话开始（startup/clear/compact） | ① `worker start` ② `context` | **读取**（注入记忆） |
| `UserPromptSubmit` | 你发出一条消息 | `session-init` | 装配/记录 |
| `PreToolUse`(Read) | 你读文件前 | `file-context`（async） | 辅助 |
| `PostToolUse` | 你每次工具调用后 | `observation`（async） | **写入**（抓取观察） |
| `Stop` | 会话结束/回合停止 | `summarize`（async） | **写入**（生成摘要） |

> 注意：写入类（`observation`、`summarize`）都是 **async**——不阻塞你的对话，后台慢慢压缩。这解释了第一层「记忆是自动、无感产生」的现象。

### 7.2 写入半环（记忆怎么产生）

```
你在会话里 Read/Edit/Bash
   │
   ▼  Claude Code 触发 PostToolUse hook
[hook 薄壳] ──HTTP──▶ [worker] : "observation"
   │
   ▼  worker 读取会话记录（transcript），交给 AI Provider 压缩
   │  （第五层：transcripts/ + sdk/ + Provider）
   ▼
写入 observations 表 (SQLite) + 向量索引 (Chroma)
   │
   ▼  会话结束触发 Stop hook → "summarize"
写入 session_summaries 表
```

对应第一层现象：`observations` 表和 `session_summaries` 表里的数据，就是这半环的产物。

### 7.3 读取半环（记忆怎么被找回并注入）

```
下次在同项目开新会话
   │
   ▼  Claude Code 触发 SessionStart hook
[hook 薄壳] ──HTTP──▶ [worker] : "context"
   │
   ▼  worker 检索相关 observation/summary
   │  （第六层：SearchManager + Chroma 混合检索）
   ▼  按「渐进式披露 + token 预算」组装成一段上下文
   │  （第六层：ContextBuilder / TokenCalculator）
   ▼
注入到会话开头 ──▶ Claude 一开场就「记得」上次的事

（此外：会话中 Claude 主动检索时，走 MCP 的 search/timeline/get_observations）
```

对应第一层现象：新会话开头多出来的那段上下文，就是这半环的产物；`mem-search` 技能则是「手动触发读取半环」。

### 7.4 一图合流：完整闭环

```
        ┌──────────────── 写入半环 ────────────────┐
Read/Edit/Bash → PostToolUse → observation → SQLite/Chroma
                                    │
                              (会话结束) Stop → summarize → session_summaries
                                    │
                                    ▼            仓库：~/.claude-mem
                                    │
下次会话 SessionStart → context → 检索 → 组装(token预算) → 注入
        └──────────────── 读取半环 ────────────────┘
```

**这就是主线问题的完整答案骨架**：
> 「我编辑一个文件 → `PostToolUse`/`observation` 把它压缩进 `observations` → 会话结束 `summarize` 生成摘要 → 下次 `SessionStart`/`context` 检索并组装 → 注入到会话开头。」

后面每一层就是把这条链上的某一环拆开看内部：
- 第三层：hook 入口（`hooks.json` → `cli/handlers/`）——**链条的触发端**
- 第四层：数据形状（`observations` 表 / schemas）——**链条流的是什么**
- 第五层：写入半环内部（transcripts → sdk 压缩 → Provider）
- 第六层：读取半环内部（检索 → context 组装 → 注入）
- 第七层：worker 如何编排这一切（路由/会话/进程守护）

> ✅ **本步小结**：一条链——`工具调用 →(PostToolUse) observation → 存储 →(Stop) summary →(下次 SessionStart) context 检索组装 → 注入`。写入端是 async 无感的，读取端在会话开头自动发生。

## 本层结束自测

试着不看图，凭记忆回答：

1. **系统里有几类进程？谁是常驻的？** → hook 薄壳（短命）、MCP 服务器（独立进程）、worker（唯一常驻）。所有入口最终打到 worker 的本地 HTTP。
2. **我改了 `src/` 的代码，怎样才能在 Claude Code 里生效？** → `npm run build-and-sync`：构建到 `plugin/` → 同步到 marketplace 目录 → 重启 worker（常驻进程必须重启才加载新代码）。
3. **一条「文件编辑」记忆，从产生到被下次会话用上，经过哪几个 hook？** → `PostToolUse`(observation) 写入 → `Stop`(summarize) 摘要 → 下次 `SessionStart`(context) 检索并注入。

三题能答上来，就带着这张「进程图 + 数据流图」进入 **第三层**——第一次真正打开代码，从链条的触发端 `hooks.json` 和 `cli/handlers/` 读起。
