# 第一层 · 会用它（黑盒视角：只看现象，不看代码）

> **目标**：先有「它到底帮我做了什么」的肌肉记忆，后面所有代码都有落点。
> **方法**：这一章一行源码都不读。只做两件事——**跑命令、看产物**。看到的每一个现象，后面章节都会回来解释「它是怎么发生的」。

## 0. 一句话先记住

> **claude-mem = 给 Claude Code 装的「跨会话长期记忆」。**
> 它自动把你每次会话里的操作（Read / Edit / Bash）压缩成「观察记录（observation）」，
> 会话结束时生成摘要，下次在同一个项目开新会话时，把相关记忆自动塞回上下文——
> **让 Claude 不用你重新讲一遍代码库和之前的决定。**

记住这句话里的三个关键名词，它们贯穿整个代码库：
- **observation（观察）**：一条被压缩过的操作记录
- **summary（会话摘要）**：一次会话结束时的总结
- **injection（注入）**：下次会话开头自动追加的上下文

## 在 Claude Code 里怎么用它（安装 + 日常操作）

> 这一节回答最实际的问题：**装好之后，我在 Claude Code 里到底要做什么？**
> 一句话预告：**几乎什么都不用做——它是自动的。** 你需要主动做的只有「装一次」和几个可选的增强动作。

### A. 安装（三选一，装一次即可）

| 方式 | 命令 | 适用 |
|---|---|---|
| ⭐ 推荐：命令行安装 | `npx claude-mem install` | 大多数人 |
| 插件市场（在 Claude Code 里） | `/plugin marketplace add thedotmack/claude-mem` 然后 `/plugin install claude-mem` | 想走插件体系 |
| 其他 IDE | `npx claude-mem install --ide opencode`（或 `antigravity`） | OpenCode / Antigravity |

安装完 **重启 Claude Code**。之后同一项目的新会话会自动带出历史上下文。

> ⚠️ **最关键的坑**：**不要**用 `npm install -g claude-mem`。那只会装 SDK 库，**不会注册 hook、不会起 worker**，等于没装记忆功能。必须用上面 `npx` 或 `/plugin` 的方式。

### B. 装完「自动」发生了什么（你不用管，但要知道）

安装脚本一次性做了三件事，之后全程自动运行：

1. **注册生命周期 hook**（写进 Claude Code 的配置）——它们在你会话的关键时刻被触发：
   `SessionStart`（会话开始，注入记忆）、`UserPromptSubmit`（你发消息）、`PostToolUse`（你每次工具调用后，抓取观察）、`Stop` / `SessionEnd`（会话结束，生成摘要）。
2. **启动常驻 worker**（后台 HTTP 服务，就是那个「大脑」）——负责压缩、存储、检索、Web UI。
3. **注册 MCP 搜索服务器**（`plugin/.mcp.json` 里的 `mcp-search`）——给 Claude 4 个可调用的记忆检索工具。

> 也就是说：**你正常写代码，claude-mem 在后台默默把你的操作变成记忆。** 无需任何手动命令。

### C. 你可以主动做的操作（都是可选增强）

虽然核心是自动的，但这些主动动作能让它更好用：

| 想做什么 | 怎么触发 | 说明 |
|---|---|---|
| **问「以前是不是干过这个」** | 直接自然语言问 Claude：「我们上次怎么修的登录 bug？」 | 触发 `mem-search` 技能 / MCP `search` 工具，跨会话检索 |
| **一次性把整个仓库读进记忆** | 在项目里输入 `/learn-codebase` | 约 5 分钟，前置填充记忆，第一次进新项目时很有用 |
| **不想让某段内容被记住** | 在消息里用 `<private>…</private>` 包起来 | 该内容不会写入存储，隐私控制 |
| **生成项目历程报告** | 让 Claude「写一份本项目的时间线报告」 | 触发 `timeline-report` 技能 |
| **看/管记忆** | 浏览器打开 worker 的 Web UI（见第 4 步） | 实时记忆流 |

Claude 在需要时会**自动调用**这 4 个 MCP 工具（你不用手动敲），它们遵循「渐进式披露」的省 token 流程：

```
search           → 拿到带 ID 的紧凑索引（每条 ~50-100 token）
timeline         → 看某条记忆前后的时间线
get_observations → 只对挑中的 ID 拉全文（每条 ~500-1000 token）
```
> 「先便宜索引、再按需拉详情」能省约 10× token——这是它检索设计的核心哲学。

### D. 改语言 / 模式（可选）

生成的记忆默认是英文。想让 observation 用中文，编辑 `~/.claude-mem/settings.json`：

```json
{
  "CLAUDE_MEM_MODE": "code--zh"
}
```

模式定义在 `plugin/modes/`（`code` 英文、`code--zh` 中文、`code--ja` 日文……，命名规律 `code--<ISO语言码>`）。`CLAUDE_MEM_MODE` 同时控制**工作流行为**和**记忆语言**。

### E. 怎么确认「真的在工作」

```bash
# 1) worker 活着吗？（有 pid 和 port 就说明后台在跑）
cat ~/.claude-mem/worker.pid

# 2) 健康检查（把端口换成上面 worker.pid 里的 port）
curl -s http://127.0.0.1:37702/health

# 3) 攒了多少记忆？（第二次会话后开始 > 0）
sqlite3 ~/.claude-mem/claude-mem.db "SELECT count(*) FROM observations;"
```

最直观的验证：**在一个用过 claude-mem 的项目里开新会话，看会话开头是否自动多出一段「历史上下文」**——那就是记忆注入生效了。

### F. 卸载

```bash
npx claude-mem uninstall
```
会干净移除 hook、worker 和 `~/.claude-mem` 数据。

> ✅ **本节小结**：`npx claude-mem install` + 重启，就完成了全部必需操作；之后 hook + worker + MCP 全自动运行。主动动作只有可选的 `/learn-codebase`、`<private>`、自然语言检索、`CLAUDE_MEM_MODE` 换语言。

## 1. 读产品介绍，建立一句话认知 —— `README.md`

打开仓库根目录的 `README.md`，只看这一段（在语言链接下面）：

> Claude-Mem seamlessly preserves context across sessions by automatically capturing tool usage
> observations, generating semantic summaries, and making them available to future sessions.

拆成三个动作，正好对应上面那句话：

| README 措辞 | 人话 | 后面哪一层讲原理 |
|---|---|---|
| capturing tool usage observations | 抓取你的工具调用并压缩 | 第五层（写入） |
| generating semantic summaries | 会话结束生成语义摘要 | 第五层（写入） |
| making them available to future sessions | 下次会话自动注入 | 第六层（读取） |

README 里还值得记住的几个「使用层」事实（都是黑盒，不涉及代码）：

- **安装方式**：`npx claude-mem install`，或在 Claude Code 里 `/plugin install claude-mem`。
  ⚠️ `npm install -g claude-mem` **只装 SDK 库，不会注册插件 hook、不会起 worker**——这是新手最常见的坑。
- **隐私**：数据只留在本机 `~/.claude-mem`，唯一出网的是「压缩时调用你配置的 AI provider」。可以用 `<private>` 标签把敏感内容排除在存储外。
- **它有个 Web Viewer UI**：worker 启动时会打印一个本地 URL，可实时看记忆流（第 4 步会打开它）。

> ✅ **本步小结**：claude-mem 是「抓取 → 摘要 → 注入」三段式的自动记忆系统，纯本地，装法要用 `npx`/`/plugin` 而不是 `npm -g`。

## 2. 亲自装一次、跑一次，观察真实产物

claude-mem 所有状态都落在一个目录：**`~/.claude-mem/`**。这是理解它最直接的窗口。

### 2.1 看一眼这个目录

```bash
ls -la ~/.claude-mem/
```

在本机实际看到的内容（已装好的样子）：

```
claude-mem.db          ← 核心！SQLite 数据库，所有记忆都在这
claude-mem.db-wal      ← SQLite 的 WAL 日志（写前日志，正常现象）
claude-mem.db-shm      ← SQLite 共享内存索引
settings.json          ← 用户配置（provider / model / runtime）
worker.pid             ← 常驻后台进程的 pid + 端口
corpora/               ← knowledge-agent 的知识库语料（第八层）
logs/                  ← worker 运行日志
backups/               ← 数据库备份
telemetry.json / supervisor.json / .env  ← 遥测 / 进程守护 / 环境变量
```

**记住一个心智模型**：`claude-mem.db` 是「数据」，`worker.pid` 指向的那个后台进程是「大脑」，
你在 Claude Code 里的每次操作都通过 hook 喂给这个后台进程，它再写进 db。

### 2.2 看配置：它现在用什么在压缩？

```bash
cat ~/.claude-mem/settings.json
```

本机实际内容：

```json
{
  "CLAUDE_MEM_RUNTIME": "worker",          // 运行时形态：常驻 worker
  "CLAUDE_MEM_PROVIDER": "claude",         // 用 Claude 做压缩
  "CLAUDE_MEM_CLAUDE_AUTH_METHOD": "subscription",
  "CLAUDE_MEM_MODEL": "claude-opus-4-7"    // 具体压缩模型
}
```

> 这就是「唯一出网的那次调用」用的模型。换成 `gemini` / `openrouter` 也是改这里（第五层会看到对应的 Provider 类）。

### 2.3 看核心产物：数据库里到底存了什么

数据库就是普通 SQLite，可以直接用 `sqlite3` 打开（macOS 自带）：

```bash
sqlite3 ~/.claude-mem/claude-mem.db ".tables"
```

会看到这些**业务表**（其余带 `_fts` 后缀的是全文搜索镜像表，先忽略）：

| 表 | 存什么 | 对应第一步的名词 |
|---|---|---|
| `observations`   | 每一条压缩后的观察记录 | **observation** |
| `session_summaries` | 每次会话的摘要 | **summary** |
| `user_prompts`   | 你发的用户提问 | prompt |
| `sdk_sessions`   | 会话元数据 | session |

看一条 observation 的「字段长什么样」（这就是记忆的形状，第四层会精读）：

```bash
sqlite3 ~/.claude-mem/claude-mem.db ".schema observations"
```

关键字段一眼扫过去就够了：
`title`（标题）、`subtitle`、`type`（bugfix/feature/decision/discovery/change）、
`narrative`（叙述）、`facts`（事实）、`concepts`（概念）、
`files_read` / `files_modified`（读了/改了哪些文件）、`project`（属于哪个项目）、`created_at`（时间）。

> 💡 **一条 observation 就是「一次操作被 AI 提炼成的一张卡片」**：谁、在哪个项目、做了什么类型的事、碰了哪些文件、结论是什么。

### 2.4 数一下现在有多少条记忆

```bash
for t in observations session_summaries user_prompts; do \
  printf "%-20s" "$t"; sqlite3 ~/.claude-mem/claude-mem.db "SELECT count(*) FROM $t;"; done
```

**本机此刻的结果是全 0** —— 这是**正常现象，不是坏了**：

> 记忆「从这个项目的第二次会话」才开始注入。第一次会话是在「播种」。
> 表结构已经建好（脚手架就绪），只是还没攒下内容。
> 想立刻填满，可以在项目里跑 `/learn-codebase`（约 5 分钟把整个仓库读进记忆，可选）。

这正好是理解产品的最好时机：**你能亲眼看着这些表从 0 长起来。**

> ✅ **本步小结**：所有东西都在 `~/.claude-mem/`；`claude-mem.db` 里 `observations` 表是记忆本体；一条 observation 是一张带 title/type/files/narrative 的卡片；空表 = 还没到第二次会话，正常。

## 3. 用自带技能体验完整闭环 —— `how-it-works` / `mem-search` / `timeline-report`

claude-mem 把「怎么用」做成了三个 Claude Code 技能（skill）。它们本身也是**最好的用法说明书**，源码在 `plugin/skills/<名字>/SKILL.md`。这一步只体验、不拆实现。

### 3.1 `how-it-works` —— 官方版「它在干嘛」

在 Claude Code 里说「how does claude-mem work?」会触发它。它的 `SKILL.md` 用三句话概括了整个系统，和本章第 0 步完全一致：

- **What**：每个 Read/Edit/Bash → 压缩成 observation；会话结束生成摘要；相关的自动注入下次 prompt。
- **When**：**记忆注入从「这个项目的第二次会话」开始**（第一次是播种）。
- **Where**：一切都在 `~/.claude-mem`，除压缩调用外不出网，`npx claude-mem uninstall` 会干净移除。

> 建议动作：读一遍 `plugin/skills/how-it-works/SKILL.md`，它比 README 更精炼。

### 3.2 `mem-search` —— 检索过去的工作（「我们之前是不是解决过这个？」）

触发场景：问「上次我们怎么修的 X？」「上周干了啥？」。
它的核心是一个 **3 层递进检索工作流**（这也是理解「读取路径」的第一手直觉）：

```
search  → 拿到带 ID 的结果索引（每条 ~50-100 token，便宜）
timeline → 围绕某条 ID 看它前后发生了什么（补上下文）
fetch   → 只对真正感兴趣的 ID 拉全文（贵，最后才做）
```

`search` 返回的是一张紧凑表格，长这样（来自 SKILL 文档示例）：

```
| ID     | Time    | T  | Title                    | Read |
|--------|---------|----|--------------------------|------|
| #11131 | 3:48 PM | 🟣 | Added JWT authentication | ~75  |
| #10942 | 2:15 PM | 🔴 | Fixed auth token expiration| ~50 |
```

> 💡 注意这个设计哲学：**先给便宜的索引，让你/让 Claude 挑，再花 token 拉详情**——README 里叫 "Progressive Disclosure（渐进式披露）"。记住这个词，第六层组装上下文时会再遇到。
> 空库时搜不出东西是正常的，等 `observations` 有数据后再回来试。

### 3.3 `timeline-report` —— 把整个项目历史写成一篇「叙事报告」

触发场景：「写一份 X 项目的时间线报告 / 项目历程」。
它会调用 **worker 的 HTTP API** 把某个项目的全部 observation 拉出来，编成一篇「Journey Into [Project]」叙事。

这里第一次出现一个你必须会算的东西——**worker 端口**。SKILL 里给的解析逻辑（也是全系统统一规则）：

```
端口 = 环境变量 CLAUDE_MEM_WORKER_PORT
     → 否则读 ~/.claude-mem/settings.json 里的 CLAUDE_MEM_WORKER_PORT
     → 否则默认 37700 + (uid % 100)
```

本机实际端口可以直接从 worker.pid 看到（下一步要用）：

```bash
cat ~/.claude-mem/worker.pid
```

本机结果：`{"pid":45496,"port":37702,...}` → **端口 37702**。

> ✅ **本步小结**：三个技能对应三种用法——`how-it-works`（问原理）、`mem-search`（三层检索找旧活）、`timeline-report`（调 worker API 生成历程报告）。它们共同揭示了「渐进式披露」和「worker 端口计算规则」两个后面反复出现的概念。

## 4. 打开后台 UI，看记忆 / 时间线 —— worker 的 `GET /` 与 `/stream`

前面反复提到的「后台大脑」worker，其实带一个**网页版实时查看器**。它就是那个常驻 HTTP 服务。

### 4.1 先确认 worker 在跑、端口是多少

```bash
cat ~/.claude-mem/worker.pid          # 拿 pid 和 port
```

本机：pid `45496`，port `37702`。用浏览器打开：

```
http://127.0.0.1:37702/
```

（host 默认 `127.0.0.1`，可被 `CLAUDE_MEM_WORKER_HOST` 覆盖。）

### 4.2 worker 都提供了哪些入口（黑盒地过一遍）

参考 `src/services/worker/README.md`（这一份文档现在只当「功能清单」看，不读实现）：

| 路由 | 作用 | 对应你在 UI 里看到的 |
|---|---|---|
| `GET /` | 查看器 UI 首页 | 记忆流主界面 |
| `GET /stream` | Server-Sent Events 实时推送 | 新记忆产生时页面自动刷新 |
| `GET /health` | 健康检查 + 版本 | —— |
| `/api/observations`、`/api/summaries`、`/api/prompts` | 存储的数据 | 列表数据来源 |
| `/api/search`、`/api/timeline`、`/api/context/*` | 搜索、时间线、上下文预览/注入 | mem-search / timeline 背后 |

可以直接 curl 感受一下（不用浏览器也行）：

```bash
PORT=$(node -e "console.log(require(require('os').homedir()+'/.claude-mem/worker.pid').port)" 2>/dev/null || echo 37702)
curl -s http://127.0.0.1:$PORT/health          # 看 worker 活着 + 版本
curl -s "http://127.0.0.1:$PORT/api/observations?limit=5"   # 看最近 5 条观察（空库会返回空）
```

> `GET /stream`（SSE）是「实时」的关键：UI 不用轮询，worker 一有新记忆就推过来。第七层讲 `SSEBroadcaster.ts` 时你会知道这条推送是怎么发出的。

> ✅ **本步小结**：worker 既是写记忆的后台，也是一个本地网站；`GET /` 是 UI，`/stream` 是实时推送，`/api/*` 是数据接口。端口按 `37700 + uid%100` 规则算，本机是 37702。

## 本层结束自测（对照「结束标准」）

> **结束标准**：能回答「一次会话结束后，我的哪些操作被记住了？下次会话开头多出来的那段上下文长什么样？」

试着用**黑盒观察到的现象**回答，不要用代码术语：

1. **哪些操作被记住了？**
   → 我在会话里的 Read / Edit / Bash 会被压缩成 `observations` 表里的卡片；每张卡有 title、type（bugfix/feature/decision/discovery/change）、碰过的文件、叙述。会话结束时还会多一条 `session_summaries` 摘要。

2. **下次会话开头多出来的那段上下文长什么样？**
   → 从**同项目的第二次会话**开始，claude-mem 会挑相关的历史 observation/summary，按「渐进式披露」组织成一段文字注入到 prompt 开头。我可以在 `http://127.0.0.1:<port>/` 的 Web Viewer 里、或用 `mem-search` 技能、或 `curl /api/context/*` 亲眼看到被注入的内容。

3. **数据在哪、可信吗？**
   → 全在 `~/.claude-mem/claude-mem.db`，纯本地；唯一出网是压缩时调用 `settings.json` 里配置的 provider（本机是 claude / opus-4-）。

如果这三题都能凭现象答上来，就可以进入 **第二层（懂它的整体结构）**——那时我们才第一次打开架构图，看这些现象背后的「进程模型 + 数据流」。
