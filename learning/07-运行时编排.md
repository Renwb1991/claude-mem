# 第七层 · 懂运行时编排（把所有能力串起来的后台进程）

> **目标**：理解那个常驻 HTTP 服务如何调度前面所有模块。
> **方法**：这一章抬升视角——前六层是「零件」，这一层看**装配图**：零件怎么被接线、被驱动、被供电（进程怎么生怎么死）。
> **承接**：第三层的 handler 把请求打到 worker 的 HTTP 端点；第五、六层是 worker 内部的压缩与检索。这一章回答**这些端点如何路由、会话如何被驱动、worker 进程本身如何被管理**。

---

## 开篇：worker 是「指挥家」，不是「演奏者」

前六层每个模块都能独立理解，但它们不会自己跑起来。真正让它们**协同工作**的是常驻 worker 进程（`worker-service.ts`），它做三件事：

1. **接线**（步骤 20）：起一个 Express HTTP 服务，把所有 Route 挂上，实例化 dbManager / sessionManager / providers / searchManager 等所有零件。
2. **驱动**（步骤 21）：把「进来的请求」变成「会话队列」，用一个常驻的 Observer 会话消费队列，把结果实时推给 UI。
3. **供电与善后**（步骤 22）：进程本身的启动（单例、健康探测）、守护（信号、并发、子进程）、优雅关闭。

```
                 ┌───────────────── worker 进程（Express + Bun）─────────────────┐
 hook / MCP ──►  │  Route 层（步骤20）                                            │
                 │    SessionRoutes / DataRoutes / SearchRoutes / ContextRoutes … │
                 │        │ 写请求                          │ 读请求               │
                 │        ▼                                 ▼                      │
                 │  SessionManager（步骤21）           SearchManager / Context     │
                 │   ├ SessionMessageBuffer（队列）      （第六层）                │
                 │   └ getMessageIterator ──► ClaudeProvider（第五层）            │
                 │                                    │ 压缩产物                   │
                 │                                    ▼                            │
                 │   storeObservations → SQLite   SSEBroadcaster ──► /stream(UI)  │
                 └────────────────────────────────────────────────────────────────┘
        supervisor + worker-spawner（步骤22）：让上面这个进程被正确地生出来、守住、干净地死
```

## 20. 路由层 —— `src/services/worker/http/routes/`

### 20.1 谁在组装这一切：`worker-service.ts` 的 `registerRoutes`

worker 启动时（`WorkerService` 构造 + `registerRoutes`）**一次性 new 出所有零件并挂上路由**（`worker-service.ts:239` 起）：

```ts
this.sessionManager = new SessionManager(this.dbManager);   // 会话/队列
this.sseBroadcaster = new SSEBroadcaster();                 // 实时推送
this.sdkAgent = /* ClaudeProvider */; this.geminiAgent = …; // 第五层 Provider
…
this.server.registerRoutes(new ViewerRoutes(sseBroadcaster, …));   // GET / 、/stream
this.server.registerRoutes(new SessionRoutes(sessionManager, dbManager, sdkAgent, …));
this.server.registerRoutes(new DataRoutes(…));
this.server.registerRoutes(new SearchRoutes(searchManager));      // 第六层
…
await this.server.listen(port, host);
```

> 💡 这就是「依赖注入」的手工版：所有共享对象（db、sessionManager、providers）在这里创建一次，注入给需要它们的 Route。**worker-service 是整个系统的组装根（composition root）。**

### 20.2 Route 分层与基类（对照第 5 步的 README）

每个 Route 是一个类，按领域切分（和第二层那张路由表对应）：

| Route 类 | 端点 | 对应前面哪层 |
|---|---|---|
| `ViewerRoutes` | `GET /`、`GET /stream` | 第一层 Web UI / SSE |
| `SessionRoutes` | `/api/sessions/{init,observations,summarize}` | 第三层写入端点、驱动第五层 |
| `SearchRoutes` | `/api/search`、`/api/timeline` | 第六层检索 |
| （context inject） | `/api/context/inject`、`/api/context/semantic` | 第六层组装 |
| `DataRoutes` | `/api/observations`、`/summaries`、`/prompts` | 存储数据列表 |
| `SettingsRoutes` / `LogsRoutes` / `ChromaRoutes` / `CorpusRoutes` / `MemoryRoutes` / `CloudSyncRoutes` | 配置/日志/向量状态/语料/记忆/云同步 | 各专项 |

它们都继承 `BaseRouteHandler`，提供三样统一能力：
- **`wrapHandler`**：把每个 handler 包进 try/catch（含 async 的 `.catch`），错误统一走 `handleError`（`AppError` → 对应 status，否则 500）——**路由层的错误纪律**，和第三层 hook 的「优雅降级」是一个家族。
- **参数强制**：`toStringParam`/`parseIntParam` 抹平 Express 5 的 `string | string[]`。
- **平台来源提取**：`getPlatformSourceFromRequest` 从 query/body/header 统一取 `platformSource`（贯穿全线的多平台标识）。

### 20.3 闭合写入环的关键一跳：`SessionRoutes`

`POST /api/sessions/observations`（第三层 observation handler 打的那个端点）在这里落地：

```
POST /api/sessions/observations
  → sessionManager.queueObservation(sessionDbId, data)   // 入队（步骤21）
  → ensureGeneratorRunning(sessionDbId, 'observation')    // 确保 Observer 会话在跑
```

`ensureGeneratorRunning`（`SessionRoutes.ts:76`）是**懒启动**：如果这个会话还没有活跃的 Observer 生成器，就调 `agent.startSession(session)`（第五层的常驻会话）并把它的 promise 挂在 `session.generatorPromise` 上；已经在跑就什么都不做。**一个会话最多一个 Observer 生成器在消费队列。**

> ✅ **本步小结**：`worker-service` 是组装根，一次性创建所有零件并按领域挂载 Route；`BaseRouteHandler` 统一错误/参数/平台来源；`SessionRoutes` 把写请求变成「入队 + 懒启动 Observer 生成器」，这是写入环在 worker 内的入口。

## 21. 会话状态与实时推送 —— `SessionManager` / `SessionMessageBuffer` / `SSEBroadcaster`

这三者构成 worker 内部的「生产线」：请求进来 → 排队 → 被 Observer 消费 → 结果推出去。

### 21.1 `SessionManager` —— 每个会话的状态机 + 队列门面

它维护 `Map<sessionDbId, ActiveSession>`，每个 `ActiveSession` 记着这次会话的一切运行态：`memorySessionId`、`abortController`、`generatorPromise`、累计 token、`claimedMessageIds` 等。关键方法：

- `queueObservation` / `queueSummarize`：把消息塞进 buffer。
- **`getMessageIterator`**：⭐ 这是和第五层的接缝——`ClaudeProvider` 的消息生成器里 `for await (message of sessionManager.getMessageIterator(...))` 消费的就是它。它内部 `buffer.drain(...)`，把排队的 observation/summarize 逐条 yield 给 Observer，并记录 `claimedMessageIds`（认领）。
- `deleteSession`：会话结束的完整拆解——abort 生成器、等它退出（30s 上限）、杀 SDK 子进程、`supervisor.reapSession`、清 buffer。

一个值得注意的健壮性决定（`initializeSession`）：**新建会话时丢弃 DB 里的旧 `memory_session_id`**（Issue #817）——因为 worker 重启后 SDK 上下文已丢，用旧 id resume 会串味，所以永远「从新捕获」（呼应第五层的 memorySessionId capture）。

### 21.2 `SessionMessageBuffer` —— 一个「会认领/确认」的内存队列

per-session 的内存队列，支持：`enqueue`（带 **toolUseId 去重**，重复返回 0）、`claim`（生成器取走）、`confirm`（存好后移除）、`resetClaimed`（没存成功的重新 yield）、`drain`（事件驱动地吐消息）。

两个设计点很关键：

- **空闲超时杀进程**：`drain` 里若 3 分钟（`IDLE_TIMEOUT_MS`）没有新消息，触发 `onIdleTimeout` → abort → 结束迭代器 → 杀掉 Observer 的 SDK 子进程。**不让常驻会话空占内存/进程。**
- **故意「不持久化」**（文件顶部那段长注释，值得一读）：这个队列**只活在 worker 进程生命周期内**，worker 一死队列就没了。为什么不做持久化？因为一条 buffered 消息是「喂给有状态、非确定性 reducer（Observer 会话）的一个片段」，旧版持久化队列在崩溃后「重放」会重新生成不同/重复的观察，甚至无限循环（那就是历史上的 retry storm）。**真正的持久真相源是 Claude Code 的 transcript JSONL，崩溃恢复路径是「转录重放」（第五层的 transcripts/）。** 所以这里刻意无持久化、无重启扫描、无 respawn-on-pending。

> 💡 这是全项目最有价值的架构决策之一：**把「可靠性」放在不可变的 transcript 上，而不是易变的中间队列上。** 值得记进你的设计经验。

### 21.3 `SSEBroadcaster` —— 把新记忆实时推给浏览器

极简：维护一个 SSE 客户端 `Set`，`broadcast(event)` 把事件写给所有连着 `/stream` 的浏览器（第一层看到的实时记忆流）。第五层 `processAgentResponse` 里的 `broadcastObservation`/`broadcastSummary` 最终就落到这里。无客户端时直接跳过（省功）。

### 21.4 worker 内部的完整闭环（把 21 串起来）

```
POST /api/sessions/observations
  → SessionManager.queueObservation → buffer.enqueue（去重）→ 发 'message' 事件
  → ensureGeneratorRunning：首次则 startSession 起常驻 Observer 会话
        Observer 的生成器 for await getMessageIterator → buffer.drain 吐出消息
        → buildObservationPrompt → Observer 压缩 → processAgentResponse
              → storeObservations（SQLite）
              → confirmClaimedMessages（从 buffer 移除）
              → SSEBroadcaster.broadcast → /stream → 浏览器实时刷新
  ...3 分钟无新消息 → idle timeout → abort → 杀 SDK 子进程 → 会话生成器结束
```

> ✅ **本步小结**：SessionManager 管会话态并用 `getMessageIterator` 喂第五层 Observer；SessionMessageBuffer 是「认领/确认 + 去重 + 空闲杀进程」的内存队列，**故意不持久化、以 transcript 重放为恢复路径**；SSEBroadcaster 把结果实时推给 UI。

## 22. worker 启停与进程守护 —— `worker-service` / `worker-spawner` / `supervisor/`

前两步是「worker 活着时怎么干活」，这一步是「worker 怎么生、怎么守、怎么死」。

### 22.1 CLI 入口：一个可执行文件的多副面孔

`worker-service.ts` 底部的 `main` 按子命令分派（`parseWorkerServiceCommand`）：

| 命令 | 作用 | 谁调用 |
|---|---|---|
| `start` / `--daemon` | 以守护进程启动 worker | hook 的 SessionStart、`npm run worker:start` |
| `stop` / `restart` / `status` | 生命周期控制 | 用户 / build-and-sync |
| `hook claude-code <event>` | **第三层的入口**（同一个可执行文件！） | 所有 hook |
| `server-*` / `cursor` / `antigravity-cli` | 云端 / 跨编辑器 | 各集成 |

> 注意：第三层反复出现的 `worker-service.cjs hook claude-code observation` 和这里的 worker 守护进程**是同一个程序的不同子命令**。hook 是「短命子命令」，`start` 是「常驻子命令」。

### 22.2 `worker-spawner.ts` —— 保证「全机只有一个 worker」

`ensureWorkerStarted(port, script)` 是 hook / MCP / CLI 想用 worker 时都会走的启动保障，返回 `ready | warming | dead`。它层层设防避免重复启动：

1. **PID 文件检查**（`cleanStalePidFile`）：PID 还活着就不重复 spawn，等它健康。
2. **健康探测**：`waitForHealth`（`/health`）→ 活着就复用。
3. **端口占用**：端口被占但没响应健康检查 → 等或判死。
4. **spawn 锁**（`acquireSpawnLock`，`worker-spawn-gate.ts`）：**同一时刻只允许一个启动者真正 spawn**，锁的输家不报错，转而去等赢家的 worker 健康。
5. Windows 有额外的 spawn 冷却（失败 2 分钟内不重试）。

> 关键概念：**单例守护 + 抢锁启动**。多个 hook 可能同时想拉起 worker，靠 PID 文件 + spawn 锁 + 健康探测三重手段保证最终只有一个 worker、其余都去复用它。

### 22.3 `supervisor/` —— 进程的「监护人」

worker 进程内跑着一个 Supervisor 单例（`supervisor/index.ts`）：

- **`start()`**：`validateWorkerPidFile()` 先校验——若已有活 PID 直接抛 `Worker already running`（**拒绝双开**）；否则初始化进程注册表、起健康检查。
- **信号处理**（`configureSignalHandlers`）：`SIGTERM/SIGINT/SIGHUP` → 触发优雅关闭 → `process.exit(0)`；防重入。
- **`process-registry.ts`**：登记所有派生出去的 **SDK 子进程**（第五层每个 Observer 会话都是一个 claude CLI 子进程）。关键能力：
  - **并发闸门 `waitForSlot(maxConcurrent)`**：限制同时活跃的 Observer 子进程数（第五层 `CLAUDE_MEM_MAX_CONCURRENT_AGENTS`，默认 2），超了排队——**防止一堆压缩任务同时开子进程打爆机器。**
  - **进程组 `pgid` 群杀**：用 `process.kill(-pgid, SIGTERM/SIGKILL)` 杀整个进程组，避免 claude CLI 留下孤儿子进程。
  - **`reapSession`**：会话结束时收割其子进程——SIGTERM 宽限 → 到期 SIGKILL。
- **`shutdown.ts` 关闭级联**（`runShutdownCascade`）：**先给所有子进程 SIGTERM → 等 5s → 幸存者 SIGKILL → 再等 1s → 清 PID 文件**。分级、有宽限、最后兜底强杀。

### 22.4 一个精妙细节：重启时的「PID 文件交接」

`shutdown.ts` 里有段注释点明：关闭级联是「濒死 worker 的最后一件事」；**重启时，濒死的老 worker 不会删掉不属于自己的 PID 文件——那是留给接班的新 worker 的**。这解释了为什么 `restart` 能无缝换代而 hook 不会扑空（hook 会等继任者健康）。这类「交接」细节是常驻服务可靠重启的关键。

> ✅ **本步小结**：同一个可执行文件按子命令扮演「hook / 守护进程 / 生命周期控制」；`worker-spawner` 用 PID 文件 + spawn 锁 + 健康探测保证**全机单例**；`supervisor` 在进程内拒绝双开、处理信号、经 `process-registry` 管控 SDK 子进程（并发闸门 + pgid 群杀 + reap），关闭走「SIGTERM→宽限→SIGKILL→清 PID」级联，并用 PID 文件交接实现无缝重启。

## 回到主线：worker 是把六层串成一条线的那根轴

```
第三层 hook ─┐
第五层 transcripts ─┤→ [SessionRoutes] → SessionManager.queue → Buffer
                    │                          │ getMessageIterator
                    │                          ▼
                    │                   ClaudeProvider（第五层 Observer）
                    │                          │ processAgentResponse
                    │        ┌─────────────────┼──────────────────┐
                    │        ▼                 ▼                  ▼
                    │  storeObservations   ChromaSync        SSEBroadcaster
                    │  (第四层 SQLite)     (向量库)          → /stream (第一层UI)
                    │
新会话 → 第三层 context handler → [context inject 路由] → 第六层 ContextBuilder/SearchManager → 注入
                    └───────── 全程活在 worker 进程里，由 supervisor 供电与善后 ──────────┘
```

**至此七层合拢**：第三层进来的请求、第四层的存储、第五层的压缩、第六层的检索，全部是 worker 进程里被路由、被会话管理、被子进程守护地跑起来的。你现在能从「一次工具调用」一路讲到「进程如何优雅退出」。

## 本层结束自测

1. **worker 里这么多零件是谁创建、怎么连起来的？** → `worker-service` 是组装根：构造时 new 出 dbManager/sessionManager/sseBroadcaster/providers/searchManager，`registerRoutes` 把 Route 类挂到 Express，注入这些共享对象。
2. **一个 observation 请求进 worker 后如何驱动压缩？** → SessionRoutes → `queueObservation`（入 buffer）→ `ensureGeneratorRunning` 懒启动 Observer 会话 → 生成器经 `getMessageIterator`/`buffer.drain` 消费 → 压缩 → 存库 + 广播。
3. **消息队列为什么不做持久化？** → buffered 消息是喂给有状态非确定性 reducer 的片段，重放会生成重复/循环（retry storm）；真相源是 transcript JSONL，恢复路径是转录重放。所以队列只活在进程生命周期内。
4. **怎么保证全机只有一个 worker？** → PID 文件（活着就复用）+ spawn 锁（同刻只一个启动者）+ 健康探测；supervisor 启动时校验 PID，已在跑就拒绝双开。
5. **压缩子进程会不会无限开？** → 不会。`waitForSlot(maxConcurrent)`（默认 2）是并发闸门，超出排队；空闲 3 分钟的会话会 abort 并 reap 掉子进程。
6. **worker 关闭时怎么不留孤儿进程？** → 关闭级联对子进程按 `pgid` 群发 SIGTERM → 宽限 5s → 幸存者 SIGKILL → 清 PID；重启时保留 PID 文件交给继任者。

六题能答上来，运行时编排就通了。主线七层已全部走完；余下 **第八层** 是可按兴趣选读的分支专题（cloud-sync / knowledge / CLI / 跨编辑器 / 测试）。
