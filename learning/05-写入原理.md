# 第五层 · 懂写入原理（记忆是怎么「生成」的）

> **目标**：主线的前半段——从原始会话记录到结构化记忆。
> **方法**：跟着数据走一遍「原始工具 I/O → 压缩 → 落库」，看清每一步谁在干活。
> **承接**：第三层把 `AgentEvent`（原始事件）投递到 worker，第四层定义了 `MemoryItem`（记忆）的形状。这一章回答**中间那步「压缩」到底怎么发生**——也是整个系统「智能」所在。

---

## 开篇：一句话看懂写入管道

claude-mem 生成记忆的核心思路，出人意料地简单也出人意料地聪明：

> **让另一个 Claude（Observer 观察者）去「旁观」你的会话，把你每次工具调用读一遍，用结构化 XML 复述成一条记忆。**

「压缩」不是传统算法，而是**一个被锁死、不能碰任何工具的 LLM agent**，它唯一的工作就是：读入「你调用了什么工具、参数是什么、结果是什么」，输出 `<observation>...</observation>`。

全景图：

```
                       ┌── 路径A：hook（第三层，Claude Code 主力）
原始工具 I/O ───────────┤
                       └── 路径B：transcripts/ 文件监听（步骤14，Codex/Cursor 等）
                                        │
                                        ▼  都汇入 worker 的会话消息队列
                          ┌─────────────────────────────────────┐
                          │  Observer SDK 会话（ClaudeProvider）   │
                          │  ── 一个「无工具权限」的常驻 LLM 会话  │
                          │  message generator 逐条喂 prompt ↓     │
                          │    buildObservationPrompt(工具I/O)     │  ← 步骤15 prompts.ts
                          │  LLM 回 <observation> / <summary> XML  │
                          └──────────────────┬──────────────────┘
                                             ▼
                          parseAgentXml(XML) → ParsedObservation   ← 步骤15 parser.ts
                                             ▼
                          processAgentResponse:
                            storeObservations → SQLite（第四层）
                            syncObservation   → Chroma 向量库
                            broadcastObservation → SSE 推到 Web UI
```

三个步骤对应本章三节：**14 = 怎么把原始 I/O 收进来（transcripts）**、**15 = 怎么压缩（sdk）**、**16 = 用哪个模型压、失败怎么办（providers）**。

## 14. ⭐ 会话记录监听与处理 —— `src/services/transcripts/`

### 14.1 先厘清：这是「第二条」摄入路径

第三层讲的 hook 路径是 Claude Code 的主力。但 Codex、Cursor 等平台不一定有 hook，它们把会话写成 `.jsonl` 转录文件。`transcripts/` 就是**盯着这些文件、把新写入的行「回放」成 worker 事件**的通道。两条路径最终都调 worker 的同一批 ingest 接口，殊途同归。

### 14.2 `watcher.ts` —— 增量 tail 一个不断追加的文件

核心是内部类 `FileTailer`：像 `tail -f` 一样只读文件「新增的部分」。关键机制：

- **按 offset 增量读**：记住上次读到的字节位置 `offset`，`fs.watch` 触发后只读 `[offset, size)` 这段新数据（`readNewData`）。
- **半行缓冲**：新数据按 `\n` 切行，最后一段可能是没写完的半行，存进 `partial` 等下次拼接——**避免解析到残缺 JSON**。
- **截断自愈**：若文件变小（`size < offset`，被轮转/重写），offset 归零重来。
- **offset 持久化**：每次读完把新 offset 通过回调交给 `state.ts` 落盘（见 14.4），**worker 重启后不会重复摄入。**

`TranscriptWatcher` 则管多文件：支持 glob 模式、递归 `fs.watch` 监听目录、从路径里用正则抽 sessionId（`extractSessionIdFromPath`），为每个匹配文件挂一个 `FileTailer`。

### 14.3 `processor.ts` —— schema 驱动把「一行 JSON」翻译成「一个事件」

`TranscriptEventProcessor.processEntry` 拿到一行解析后的 JSON，做的事是**配置驱动**的（schema 结构在 `types.ts`，具体 schema 在配置文件里，如根目录 `transcript-watch.example.json`）：

```
一行 entry
  → 遍历 schema.events，用 matchesRule 判断命中哪个事件
  → resolveFields 按 FieldSpec 从 entry 里抽字段（支持 path/coalesce/default）
  → 按 event.action 分派：
      session_init / user_message / assistant_message
      tool_use / tool_result / observation / file_edit / session_end
```

它自己维护 `SessionState`（每个会话的 cwd/project/lastUserMessage 等），因为转录文件是**扁平的事件流**，需要跨行拼装上下文。最能体现「聪明」的是 **tool_use / tool_result 配对**：

- 某些平台工具「调用」和「结果」分两行出现。`handleToolUse` 若拿到调用但还没结果，就把它暂存进 `pendingTools`（按 `toolId`）；
- `handleToolResult` 再按 `toolId` 取回配对，凑齐 `toolName + toolInput + toolResponse` 才 `sendObservation`。

`sendObservation` 最终调 `ingestObservation(...)`（worker 内部），`sendFileEdit` 复用第三层的 `fileEditHandler`，`session_end` 触发 `queueSummary`（POST `/api/sessions/summarize`）——**又回到第三层那批端点**。

> 顺带：`updateContext` 会把注入上下文写进项目的 `AGENTS.md`（给 Codex 这类「靠读文件获取上下文」的平台用），并且做了**路径穿越防护**（只允许写在 cwd 或数据目录下），是个值得注意的安全细节。

### 14.4 `state.ts` —— 就是 offset 的存取

极简：`{ offsets: Record<文件路径, 字节偏移> }` 读/写一个 JSON 文件，容错（读失败就从空开始）。它是「增量、不重复摄入」的账本。

> ✅ **本步小结**：transcripts 是「非 hook 平台」的摄入通道。`watcher` 用 offset 增量 tail 文件（半行缓冲 + 截断自愈 + offset 持久化），`processor` 用 schema 把扁平事件流翻译并跨行配对成 observation/summary，`state` 记 offset。产物和 hook 路径一样打进 worker 的 ingest 端点。

## 15. ⭐ 压缩核心：提示词 + 输出解析 —— `src/sdk/`

这一节是「记忆的智能」所在。四个文件各司一职：**prompts 出题、parser 收卷、classifier 判卷类型、hardened-options 关小黑屋。**

### 15.1 `prompts.ts` —— 给 Observer 出的「填空题」

Observer 不是自由发挥，而是被喂一个**结构化 XML 骨架**要求照填。所有 prompt 都由 `ModeConfig` 拼成——**这正是第一层 `CLAUDE_MEM_MODE`（如 `code--zh`）的落地点**：模式决定了提示词语言、观察类型集合、各种引导语。

四种 prompt：

| 函数 | 何时用 | 产出要求 |
|---|---|---|
| `buildInitPrompt` | 会话第一条 | 交代 Observer 身份/职责 + 观察骨架 |
| `buildContinuationPrompt` | 同会话后续 | 精简版续接 |
| `buildObservationPrompt` | **每条工具 I/O** | 把 `tool_name/参数/结果` 包成 `<observed_from_primary_session>`，要求回 `<observation>` |
| `buildSummaryPrompt` | 会话结束 | 强制回 `<summary>`（三令五申「不许用 observation 标签」） |

观察骨架 `<observation>` 要求填：`type`（枚举，来自 mode 的 `observation_types`）、`title/subtitle`、`facts[]`、`narrative`、`concepts[]`、`files_read[]`、`files_modified[]`——**正好是第四层 `MemoryItem` 的字段**。至此闭环：prompt 的填空项 = 记忆的数据结构。

一个必须理解的健壮性设计——**超长字段截断**（`truncateObservationField`）：

- 单个 `<parameters>`/`<outcome>` 上限 `16000` 字符（≈4k token）。
- 超了就**保头 60% + 保尾 30%**，中间用 `<elided chars=... />` 标记替换。
- 原因写在注释里：一次 Read 可能返回 130k 字符的大文件（#2468），不截断会撑爆 Observer 的上下文窗口、整个 SDK 会话报「prompt too long」而崩。保头保尾是因为「工具 signal 通常在开头（路径/命令/错误头）和结尾（最终错误行）」。
- 还明确告诉模型「看到 elided 标记就别脑补被删的部分」——防幻觉。

### 15.2 `parser.ts` —— 把 XML「收卷」成结构体

`parseAgentXml(raw)` 把 Observer 的 XML 文本转回 `ParsedObservation[]` / `ParsedSummary`。要点：

- **只认 XML**：先找第一个根标签 `<observation>` 或 `<summary>`，都没有就 `{ valid: false }`。
- **去围栏**：仅当整段是单个 ```` ```xml ```` 代码块时才剥（注释解释：乱剥会破坏内部示例，见 PR #2282）。
- **type 兜底校验**：解析出的 `type` 必须在当前 mode 的 `observation_types` 里，否则记 error 并回退到第一个合法类型——**坏 type 不会污染数据**（和第四层 CHECK 约束呼应）。
- **拒空**：所有内容字段都空的 observation 直接跳过；没有任何子标签的 `<summary>` 判为「假阳性」拒绝。
- **skip 协议**：`<skip_summary reason="..."/>` 表示「这次不值得记」，合法地返回空。

### 15.3 `output-classifier.ts` —— 判卷：这份输出是哪一类

Observer 有时不回 XML（回大白话、或空）。历史上这类会被静默丢弃，导致「观察数一直是 0 却没人知道」。分类器把非 XML 情况分开，让日志能看见：

- `xml`：含可解析根标签——正常。
- `idle`：空/纯空白——良性，模型「无话可说」。
- `prose`：其他大白话——不入库，但会 log 一段预览（`previewOutput`）**让丢弃可见**。

外加 `isQuotaLimitedObserverOutput`：识别「把配额用尽写成了聊天文字」的情况——配额暂停要保住已认领的工作，不能当普通 prose 丢掉。

### 15.4 `hardened-options.ts` —— 把 Observer 关进「无工具小黑屋」

这是**安全核心**。Observer 的系统提示声称「你没有工具权限」，但光靠提示不够——万一 SDK 出了个新内置工具没进黑名单，Observer 就可能真去 Edit/Write/Bash 用户的源码。`buildHardenedSdkOptions` 用**纵深防御**把这句承诺变成配置层的硬事实，六层冗余、缺一不可：

| 层 | 配置 | 作用 |
|---|---|---|
| belt | `tools: []` | SDK 层禁用**所有**内置工具 |
| empty allow | `allowedTools: []` | 没有任何工具被自动批准 |
| suspenders | `disallowedTools: [...]` | 显式拉黑 Bash/Read/Write/Edit… |
| braces | `permissionMode: 'dontAsk'` | 未预批准即拒绝（这里没预批任何） |
| backstop | `canUseTool` | 每次调用一律 deny + 写审计日志 |
| isolation | `cwd` 牢笼 + `mcpServers:{}` + `settingSources:[]` + `additionalDirectories:[]` | 禁继承设置/MCP、禁文件系统逃逸 |

> 💡 「冗余本身就是安全属性」——删掉任何一层都不能重新打开缺口。这是很值得学习的防御式设计范式。Observer 和 KnowledgeAgent（第八层）两个调用点都**必须**走这个函数，避免锁定策略在两处漂移。

> ✅ **本步小结**：prompts 用 ModeConfig 出结构化填空题（字段 = MemoryItem 字段，超长自动保头尾截断防爆）；parser 把 XML 收成结构体并做 type 兜底/拒空/skip；classifier 让「非 XML 输出」可见而非静默丢；hardened-options 用六层纵深防御把 Observer 锁死为无工具。

## 16. 多模型 Provider 适配与容错 —— `src/services/worker/`

### 16.1 两种 Provider 形态

「用哪个模型压缩」由 `CLAUDE_MEM_PROVIDER`（第一层见过，本机是 `claude`）决定。实现分两类：

| | **ClaudeProvider** | **Gemini / OpenRouter / OpenAICompatible** |
|---|---|---|
| 机制 | Agent SDK 的 `query()`，起一个 claude CLI 子进程 | 直接 `fetch()` 调 HTTP API |
| 会话 | **常驻会话**，跨 prompt `resume` 复用上下文（省 token） | 无常驻会话，逐次请求 |
| 重试 | SDK 自身 + 分类错误 | `retry.ts` 的 `withRetry` |
| 共享 | 都用同一套 `prompts.ts` 出题、`parser.ts` 收卷、`processAgentResponse` 落库 | 同左 |

### 16.2 ClaudeProvider 的精髓：一个「常驻 Observer 会话 + 消息生成器」

`ClaudeProvider.startSession` 是本章最值得细读的一段。它不是「每条观察调一次 API」，而是**开一个长期存在的 SDK 会话，用 async generator 源源不断喂 prompt**：

```
query({ prompt: messageGenerator, options: buildHardenedSdkOptions({...}) })

createMessageGenerator（async 生成器）：
  1) 先 yield 初始/续接 prompt（buildInitPrompt / buildContinuationPrompt）
  2) 然后 for await 从 sessionManager 拉队列消息：
       type==='observation' → yield buildObservationPrompt(工具I/O)
       type==='summarize'   → yield buildSummaryPrompt(...)
```

主循环 `for await (message of queryResult)` 消费模型的回应：

- **捕获 memorySessionId**：SDK 分配的 `session_id` 被记住并写库（`ensureMemorySessionIdRegistered`），下次同会话用 `resume: memorySessionId` 续接——**这就是省 token 的关键：Observer 记得之前的上下文，靠 prompt 缓存增量压缩。**
- **落库**：`message.type==='assistant'` 时把文本交给 `processAgentResponse`（→ parseAgentXml → storeObservations → Chroma → 广播）。
- **token/成本计量**：累计 input/output token、按 `result` 消息的 `total_cost_usd` 增量算单次压缩成本，写遥测。
- **配额守卫**（#2234）：SDK 会推 `system/rate_limit` 事件带订阅配额快照；跨过阈值就 `abort()` 当前会话（订阅用户保护，API-key 用户豁免）。

### 16.3 错误分类 + 重试：`provider-errors.ts` + `retry.ts`

**统一错误模型**（`provider-errors.ts`）：`ClassifiedProviderError` 带一个 `kind`：

```
transient | rate_limit | quota_exhausted | auth_invalid | setup_required | unrecoverable
```

每个 Provider 有自己的「翻译官」把原始错误映射成 kind：
- `classifyClaudeError`：`ENOENT/spawn` → `setup_required`；401/403 → `auth_invalid`；529/OverloadedError → `transient`；429 → `rate_limit`；`Prompt is too long`/400 → `unrecoverable`；5xx → `transient`；其余默认 `transient`。
- `classifyGeminiError`：结构类似，走 HTTP status。

**重试策略**（`retry.ts` 的 `withRetry`，Gemini/OpenRouter 用）：

- **由 kind 驱动**，不是看原始 HTTP 码：只有 `transient` / `rate_limit` 才重试（`isRetryableKind`）。
- **指数退避 + 抖动**：`100 * 2^attempt + random(50)`，封顶 30s；`rate_limit` 若带 `Retry-After` 则优先用它（`parseRetryAfterMs`）。
- **上限 2 次**：因为这些 POST 不严格幂等，不宜猛重试。
- 每次尝试有独立超时的 `AbortController`，且退避期间可被外部 abort 打断。

> 设计意图对比第三层：hook 层的哲学是「失败也别打断用户」；provider 层的哲学是「按错误性质决定退避/放弃，绝不盲目死重试」。`unrecoverable`（如配置错、prompt 过长）立即放弃，避免无限重试一个永久错误（#2357/#2656 就是这类真实教训）。

### 16.4 记忆「落地」的最后一步：`agents/ResponseProcessor.ts`

`processAgentResponse` 是压缩产物入库的收口（`agents/` 目录）：

```
parseAgentXml(text)               → 结构化
  ├ 无效？ classifyObserverOutput → idle 静默 / prose 记日志 / 配额特判
  └ 有效 → storeObservations()    → 写 SQLite（第四层的表）
          → getChromaSync().syncObservation() → 写 Chroma 向量库（失败仅告警，不阻断）
          → broadcastObservation() → SSE 推给 Web UI（第一层看到的实时流）
```

> 注意「Chroma 失败仅告警、继续」——关键词检索（SQLite FTS5）是主，向量检索（Chroma）是增强，后者挂了不影响记忆落库。这个取舍第六层会再遇到。

> ✅ **本步小结**：ClaudeProvider 用「常驻会话 + 消息生成器 + resume 复用」增量压缩；HTTP 类 Provider 直连 + withRetry。错误统一成 `ClassifiedProviderError.kind`，重试由 kind 驱动（指数退避、上限2、尊重 Retry-After），`unrecoverable` 立即放弃。产物经 `processAgentResponse` 落 SQLite + Chroma + SSE 广播。

## 回到主线：写入半环完整走一遍

```
你编辑文件 file.ts
 → (hook 或 transcripts) 原始工具 I/O 进入 worker 会话队列
 → ClaudeProvider 的消息生成器 yield buildObservationPrompt(工具I/O)
 → Observer（无工具的 Claude）读入，回 <observation><type>change</type>
     <title>编辑 file.ts …</title><files_modified><file>file.ts</file>...
 → parseAgentXml → ParsedObservation
 → processAgentResponse → storeObservations（SQLite）+ Chroma + 广播
 ────────────────────────────────────────────────
 会话结束 → buildSummaryPrompt → <summary> → 存 session_summaries
```

**主线问题的前半段到此闭合**：你的一次编辑，已经变成 `observations` 表里一条带 `title/type/files_modified` 的结构化记忆，并进了向量索引。下一层（第六层）就是它如何被检索出来、组装成上下文注入回去。

## 本层结束自测

1. **「压缩」到底是什么？** → 一个被 `hardened-options` 锁成「无工具」的 Observer LLM 会话，读入原始工具 I/O，按 `prompts.ts` 的 XML 骨架复述成 `<observation>`。不是传统算法，是 LLM 结构化改写。
2. **为什么大文件 Read 不会撑爆 Observer？** → `truncateObservationField` 把每个字段截到 16k 字符，保头 60% 尾 30%、中间打 `<elided>` 标记，并叮嘱模型别脑补。
3. **hook 已经能摄入，为什么还要 transcripts？** → 给没有 hook 的平台（Codex/Cursor）用：tail JSONL 转录文件，用 offset 增量读、schema 回放成事件，最终打进同一批 worker 端点。
4. **Claude 和 Gemini 两种 Provider 最大区别？** → Claude 走 Agent SDK 常驻会话（resume 复用上下文、SDK 子进程）；Gemini 直连 HTTP + `withRetry`。两者共用 prompts/parser/落库。
5. **一个 429 和一个「prompt too long」，重试策略一样吗？** → 不一样：429→`rate_limit` 会退避重试（尊重 Retry-After）；prompt too long→`unrecoverable` 立即放弃。由 `ClassifiedProviderError.kind` 决定。
6. **Observer 回了一句大白话而不是 XML，会怎样？** → `classifyObserverOutput` 判为 `prose`，不入库，但 log 一段预览让丢弃可见（不再静默）。

六题能答上来，写入原理就通了。下一层 **第六层** 进入读取半环：`SearchManager`/Chroma 检索 + `ContextBuilder` 组装 + token 预算 → 把记忆注入回新会话。
