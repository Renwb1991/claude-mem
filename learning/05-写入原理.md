# 第五层 · 懂写入原理（记忆是怎么「生成」的）

> **目标**：走通主线的前半段——**从原始会话记录，到一条结构化 `MemoryItem`**。
> **承接**：第三层看的是 hook 怎么把事件打进 worker；第四层固定住了「货物的形状」（进来的是 `AgentEvent`，存下的是 `MemoryItem`）。这一层回答那个最关键的问题——**中间那步「压缩/提炼」到底发生了什么。**
> **方法**：只看「写入」，不看「取回」（检索是第六层）。

---

## 开篇必读：一个反直觉但决定性的事实

大多数人以为「压缩」是一段普通的字符串处理代码——截断、去重、抽关键词。**不是。**

> 🔑 **claude-mem 的压缩，本身就是一次 AI 调用。** worker 会再启动一个**被彻底锁死、不给任何工具**的 Claude（源码里叫 **Observer / 观察者**），把你刚才那次工具活动（读了什么文件、跑了什么命令、输出是什么）喂给它，让它**用「旁观者」的身份，把这段活动提炼成结构化的 `<observation>` XML**。

这解释了本层最容易困惑的三件事，先记在心里：

1. **为什么要有一套精心设计的提示词（`prompts.ts`）**——因为要「指挥」这个观察者模型输出规定格式。
2. **为什么要有解析器（`parser.ts`）和输出分类器**——因为模型的输出是**文本 XML**，不是保证合法的 JSON，必须解析 + 容错。
3. **为什么要有多 Provider 和一整套错误分类/重试**——因为这个「提炼」既可以让本地 Claude SDK 做，也可以甩给 Gemini / OpenRouter 的 HTTP API 做，而 AI 调用天然会超时、限流、报错。

带着「压缩 = 二次 AI 调用」这个认知往下读，三个步骤会瞬间连成一条线。

---

## 本层全景：写入主线的四段接力

```
① 摄入          ② 排队            ③ 压缩（AI 调用）           ④ 落库
─────────────   ────────────────  ─────────────────────────   ──────────────
原始会话记录  →  worker 观察队列  →  Observer 模型读活动、吐 XML  →  storeObservations
(hook / 监听)                        prompts.ts 出题                 → 第四层的表
                                     parser.ts 阅卷                  → Chroma / 广播
```

- **第 14 步（transcripts）** 讲的是 **① 摄入的第二条路径**——盯着会话记录文件，把各家格式归一成观察事件。
- **第 15 步（sdk）** 讲的是 **③ 压缩的两个半场**：`prompts.ts` 出题（给观察者的提示词）、`parser.ts` + `output-classifier.ts` 阅卷（把 XML 解析回结构化数据）。
- **第 16 步（worker providers）** 讲的是 **③ 由谁来答题**：Claude / Gemini / OpenRouter 三个 Provider 的适配与容错。

> 💡 ④ 落库（`ResponseProcessor.storeObservations` → 第四层的存储层）是本层的终点、下一层的起点，本章末尾会点到，细节在第四/六层。

## 14. ⭐ 会话记录监听与处理 —— `src/services/transcripts/`

### 14.1 先解决一个疑问：不是已经有 hook 了吗？

第三层看到 hook（`PostToolUse` 等）会主动把事件 POST 给 worker。那这里再搞一套「监听会话记录文件」是重复吗？

不是。**它们是「两条摄入路径」，服务不同场景**：

| | **Hook 路径（第三层）** | **Transcript 监听（本步）** |
|---|---|---|
| 触发方式 | 平台主动回调（push） | 主动盯文件、增量读（pull/tail） |
| 主要面向 | Claude Code（原生支持 hook） | **没有 hook 机制的平台**：Codex、其它写 `.jsonl` 记录的 agent |
| 归一手段 | handler 里写死字段 | **声明式 schema**（配置驱动，不改代码就能接新平台） |
| 汇入点 | worker 的观察端点 | **同一个** worker 观察端点（`ingestObservation`） |

> 🔑 记住这句：**两条路不同源，但同归**——最终都变成 worker 观察队列里的一条待压缩事件。所以本步的产物，和第三层 handler 的产物，是同一种「货物」。

### 14.2 `watcher.ts` —— 增量追读一个只会变长的文件

会话记录是 `.jsonl`（每行一个 JSON）。这类文件的特点是**只在末尾追加**。`FileTailer` 就是干「tail -f」的：

```
构造时给一个 initialOffset（上次读到哪）
fs.watch 监听文件变化 → readNewData()：
  1. stat 拿当前 size
  2. size < offset ？→ 文件被截断/重写了，offset 归零重读
  3. size == offset ？→ 没新内容，返回
  4. 只读 [offset, size) 这段新增字节
  5. offset 前移，回调 onOffset（持久化）
  6. 按 \n 切行；最后一段没换行的存进 partial，等下次拼接
```

三个健壮性细节值得记：

- **断点续读**：`onOffset` 回调把每个文件读到的偏移量存进 `state.ts`（见 14.4）。worker 重启后不会从头重读、不会重复压缩。
- **半行缓冲**：`this.tailState.partial` 处理「一行还没写完就触发了 watch」的情况——把不完整的尾巴留到下次。
- **截断自愈**：`size < offset` 说明文件被清空或轮转，offset 归零而不是崩溃。

`TranscriptWatcher` 在 `FileTailer` 之上做**发现**：支持 glob（`~/.codex/sessions/**/*.jsonl`）、递归 `fs.watch` 监听目录、新文件出现时自动挂 tailer。每行读出来 → `JSON.parse` → 交给 processor。解析失败只 `debug` 一条日志、跳过这一行——**一行坏 JSON 不拖垮整个监听**（又是那个「局部坏数据不拖垮全局」的哲学）。

### 14.3 `types.ts` + schema —— 用「声明式配置」抹平各平台差异

这是本步最巧妙的设计。不同 agent 的 `.jsonl` 字段五花八门，claude-mem **不为每个平台写一套解析代码，而是让平台用一份 JSON schema 自我描述**：

```jsonc
// transcript-watch.example.json（Codex 的 schema，节选）
{
  "name": "tool-use",
  "match": { "path": "payload.type", "in": ["function_call", "custom_tool_call"] },
  "action": "tool_use",                    // ← 归一成本项目的标准动作
  "fields": {
    "toolName": { "coalesce": ["payload.name", "payload.type"] },  // 多路取值
    "toolInput": { "coalesce": ["payload.arguments", "payload.input", "payload.command"] }
  }
}
```

三个概念（`types.ts` 里的类型）：

- **`MatchRule`**：这一行 JSON 属于哪种事件（`equals`/`in`/`regex`/`exists`…）。
- **`EventAction`**：归一后的标准动作，就那么几种——`tool_use` / `tool_result` / `observation` / `session_init` / `session_end` …
- **`FieldSpec`**：怎么从原始 JSON 里取字段。`coalesce`（多路径按序取第一个非空）是精髓——它吸收了各平台字段命名的差异。

> 💡 这就是「配置驱动接入」：接一个新 agent 平台，**理想情况下只写一份 schema，不改一行代码**。schema 是「各平台方言 → claude-mem 标准动作」的翻译词典。

### 14.4 `processor.ts` —— 把「标准动作」翻译成「观察事件」

`TranscriptEventProcessor` 拿到一条已 `JSON.parse` 的记录，做三件事：

**第一，维护每次会话的内存状态**（`SessionState`：`sessionId`/`cwd`/`project`/`lastUserMessage`/`pendingTools`）。同一会话的多行记录共享这个状态。

**第二，按 `action` 分发**（`handleEvent` 里的 switch）：

| action | 干什么 |
|---|---|
| `session_init` | 调 `sessionInitHandler`（复用第三层的 handler），可选写 AGENTS.md |
| `tool_use` / `tool_result` | 组装工具活动 → `sendObservation` → `ingestObservation`（打进 worker） |
| `observation` | 直接送观察 |
| `session_end` | `queueSummary`（POST `/api/sessions/summarize`）+ 更新上下文 + 清理会话状态 |

**第三，处理「工具调用」与「工具结果」分两行到达的情况**（`pendingTools` map）：

```
tool_use 先到、但还没结果  →  暂存进 session.pendingTools[toolId]
tool_result 后到           →  按 toolId 取回入参、配对，凑成完整观察再送出
```

这跟第四层「读全/写瘦」一样，是个反复出现的小模式：**异步到达的两半，用一个 id 在内存里配对。**

还有个安全细节值得一看——`updateContext` 写 AGENTS.md 前，会校验目标路径必须落在 `cwd` 或 `DATA_DIR` 之内，否则拒绝并记 `SECURITY` 日志（防路径穿越）。第三层的「优雅降级」、这里的「路径白名单」，是同一套防御姿态。

> ✅ **本步小结**：transcript 监听是 hook 之外的第二条摄入路径，专治没有 hook 的平台。`watcher.ts` 增量 tail 文件（偏移持久化、半行缓冲、截断自愈）；schema（`types.ts`）用声明式配置把各平台方言翻译成标准动作；`processor.ts` 按动作分发、内存里配对 tool_use/tool_result，最终 `ingestObservation` 汇入与 hook 相同的 worker 队列。

## 15. ⭐ 压缩核心：提示词 + 输出解析 —— `src/sdk/`

这是本层的心脏。把它拆成「出题」和「阅卷」两半来看。

### 15.1 出题：`prompts.ts` —— 给观察者模型的四类提示词

worker 要把队列里的观察事件变成一段「给 Observer 的提问」。`prompts.ts` 造四类提示词：

| 函数 | 什么时候用 | 大意 |
|---|---|---|
| `buildInitPrompt` | 会话第一次压缩 | 立人设（系统身份 + 观察者角色 + 空间感知）+ 给出 XML 骨架 |
| `buildObservationPrompt` | 每个待压缩的工具活动 | 把 `tool_name`/`parameters`/`outcome` 塞进模板，要求回 `<observation>` |
| `buildSummaryPrompt` | 会话结束 | 要求回 `<summary>`（request/investigated/learned/…） |
| `buildContinuationPrompt` | 同一会话的后续压缩 | 类似 init，但走「续接」措辞 |

两个关键设计：

**① 输出骨架是 XML，且由「模式（mode）」参数化。** `observationSkeleton(mode)` 拼出一份 `<observation>` 模板，里面 `<type>`、字段引导语、示例，全来自 `mode`（对应 `plugin/modes/*.json`——所以同一套代码能切「代码模式 / 法律学习模式 / meme 模式」等不同人设）。**提示词不是硬编码的，是数据驱动的。**

**② 超大字段的「掐头去尾」截断（`truncateObservationField`）**——本文件最该记的工程细节：

```
单字段上限 16k 字符（≈4k token）。超了就：
  保留头部 60% + 尾部 30%，中间用 <elided chars=... /> 标记替换
```

为什么头尾都留？源码注释说得很清楚：**头部**通常是工具的规范信号（文件路径、错误信息、命令头），**尾部**通常是错误/最终结论。丢的是中间。而且**显式插入 `<elided>` 标记**——好让观察者模型「知道自己被截断了」，不去编造缺失部分的细节。

> 💡 这一处直接对应第四层提过的隐患：一次 `Read` 读了个 13 万字符的大文件（issue #2468），如果原样塞进提示词会把上下文窗口撑爆、导致整个 SDK 会话 `prompt is too long` 而中止。截断就是那道保险丝。

### 15.2 阅卷（上）：`parser.ts` —— 把文本 XML 解析回结构化数据

模型答完，回来的是一段**文本形式的 XML**（不是工具调用、不是保证合法的 JSON）。`parseAgentXml` 负责把它变回 `ParsedObservation[]` / `ParsedSummary`：

```
parseAgentXml(raw):
  1. stripCodeFences   ——只在「整段都被 ```xml 包住」时才剥，避免误伤内部示例
  2. 命中 <skip_summary/> ？→ 合法的「跳过」信号
  3. 找第一个根标签 <observation> 或 <summary>，决定走哪条解析
  4. 正则逐块抽字段（extractField / extractArrayElements）
  5. 校验 & 清洗：
       - type 必须在 mode 允许的枚举内，否则回退到第一个合法值 + 记 error
       - 从 concepts 里剔掉误混入的 type
       - 所有内容字段都空的 observation → 丢弃（视为无效）
```

两个要点：

- **这是「文本协议」，不是「结构化 API」。** 文件顶部有 `TODO(#2233)`：将来想迁移到 Anthropic 的 tool-use API 拿确定性 JSON，「当前这条文本-XML 路径是过渡桥」。读到正则解析别惊讶——这是有意的临时方案。
- **解析器也是一道校验闸**：type 非法就回退、空块就丢弃、假阳性 summary（有标签没内容）直接拒。**坏输出在解析边界被挡下**，和第四层「Zod 在存储边界挡坏数据」是同一层防御思想的两个位置。

### 15.3 阅卷（下）：`output-classifier.ts` —— 让「被丢弃的批次」看得见

模型不总是乖乖吐 XML，有时回一句大白话、有时空着、有时回「你的额度用完了」。历史上这些都被 `parseAgentXml` 一律判 `{valid:false}` 然后**静默丢弃**——结果就是「观察数一直是 0，还查不出原因」。分类器就是来消灭这种静默的：

```
classifyObserverOutput(raw):
  'xml'   —— 含可解析的根标签（结构闸放行，能不能出行由 parser 定）
  'idle'  —— 空白（模型没啥可说，良性）
  'prose' —— 其它非 XML 文本（对话腔，不该入库）
```

外加 `isQuotaLimitedObserverOutput`：用一组正则识别「Claude usage limit reached / weekly quota…」这类**把限额提示当正文返回**的情况。识别出来后（见 `ResponseProcessor`）不是丢弃，而是**暂停生成、保住这批未压缩的观察**，等额度恢复再压——避免限额期间把待办观察白白吞掉。

> 💡 主题浮现：本层反复在做「让沉默变成信号」。坏 JSON 记一条 debug、被丢批次记一条带预览的 warn、限额被识别成可恢复的暂停。**可观测性是这套流水线的一等公民。**

### 15.4 `hardened-options.ts` —— 把「你没有工具」从提示词承诺变成配置铁律

Observer 的系统提示词里写着「你无权使用任何工具」。但**提示词只是「请求」，模型理论上仍可能去调工具**。这个文件把那句承诺**在 SDK 配置层坐实**，用的是「六层防御，无单点」：

| 层 | 配置 | 作用 |
|---|---|---|
| 皮带 | `tools: []` | SDK 真正的限制性白名单——禁用所有内置工具 |
| — | `allowedTools: []` | 无任何自动批准 |
| 背带 | `disallowedTools: [...]` | 显式逐个拒（Bash/Read/Write/Edit/…） |
| 扣带 | `permissionMode: 'dontAsk'` | 未预批准即拒（这里啥都没预批） |
| 兜底 | `canUseTool` | **拒绝每一次调用，并写审计日志** |
| 隔离 | `cwd` 牢笼 + `mcpServers:{}` + `settingSources:[]` + … | 就算工具没禁掉，也切断文件/设置/MCP 逃逸路径 |

> 🔑 源码原话：**「冗余本身就是安全属性——去掉任何一层都不能重新打开缺口。」** 威胁模型也写得很清楚：假如未来 SDK 出了个不在拒绝名单里的新内置工具，只靠 `disallowedTools` 就漏了；`tools: []` 是真正的兜底。这是「记忆生成」这件事里被最认真对待的安全边界——**一个读你全部工具活动的旁观者，绝不能反过来动你的代码。**

> ✅ **本步小结**：`prompts.ts` 出题（XML 骨架 + mode 参数化 + 超大字段掐头去尾截断）；`parser.ts` 阅卷（正则解析文本-XML，type 校验/空块丢弃，注意这是 #2233 的过渡桥）；`output-classifier.ts` 把 idle/prose/quota 分类，让被丢批次可见、让限额可恢复；`hardened-options.ts` 用六层防御把观察者锁成「零工具」。

## 16. 多模型 Provider 适配与容错 —— `src/services/worker/`

前一步造好了「题」和「阅卷规则」。这一步的问题是：**谁来答题？** claude-mem 支持三家，同一套提示词、同一套解析器，可切换后端。

### 16.1 三个 Provider 与选择逻辑

| Provider | 怎么调模型 | 特点 |
|---|---|---|
| `ClaudeProvider` | Claude Agent **SDK**（起子进程，`query()`） | 复用你本机的 Claude 登录态；流式；带完整用量/成本回报 |
| `GeminiProvider` | 直接 **HTTP fetch** Google API | 轻量；自带 RPM 限速 |
| `OpenRouterProvider` | HTTP（OpenAI 兼容） | 走 OpenRouter 网关 |

选择在 `SessionRoutes.getSelectedProvider()`，按设置优先级：`openrouter`（选中且可用）> `gemini`（选中且可用）> **`claude`（默认兜底）**。

> 💡 后两者都继承 `OpenAICompatibleProvider` 基类，把「HTTP 请求-重试-解析」的骨架抽公共了，各自只填「怎么拼请求、怎么读响应」。而 `ClaudeProvider` 因为走 SDK 子进程、机制差别大，是独立实现。

### 16.2 `ClaudeProvider.startSession` —— 一次压缩会话的完整生命周期

这是本层代码量最大的一块，但骨架就一句：**用一个「消息生成器」喂给 SDK 的 `query()`，再消费它吐回的流。**

```
startSession:
  1. 找 Claude 可执行文件（找不到 → setup_required 错误，不重试）
  2. 解析模型 id（含 $TIER 别名，见 16.4）
  3. 用 buildHardenedSdkOptions 锁死会话（第 15.4 步）
  4. query({ prompt: 消息生成器, options })
  5. for await 消费返回流：
       - system/rate_limit 事件  → 存额度快照，越线就中止（quota guard）
       - 捕获 memorySessionId    → 回写 DB（续接时靠它 resume）
       - assistant 消息          → 累加 token 用量 → processAgentResponse（阅卷+落库）
       - result 消息             → 结算本轮真实用量与成本 → 打点遥测
```

**消息生成器（`createMessageGenerator`）** 是理解「压缩节奏」的钥匙：

```
先 yield 一条 init/continuation 提示词（立人设）
然后 for await 从 SessionManager 拉队列里的消息：
   type === 'observation' → yield buildObservationPrompt(...)
   type === 'summarize'   → yield buildSummaryPrompt(...)
```

也就是说——**观察者是一个「长会话」**：开场立好人设，之后你每产生一次工具活动，就往这个会话里追一条「请把这段提炼成 observation」的问，模型答一条 XML。会话结束时追一条「请总结」。`resume`（用 `memorySessionId`）让 worker 重启后能接回同一个观察者会话，而不是每次从头立人设。

> ⚠️ 一个容易看漏但重要的点：`assistant` 消息里的 `usage.output_tokens` 是**流式早期的占位值**（个位数），不能用来算成本。真实用量在 `result` 消息里——所以遥测事件被「暂存」在 assistant 阶段、等 `result` 到了再补齐 token 和成本发出。这是「不用估算值污染指标」的洁癖。

### 16.3 错误分类与重试：`provider-errors.ts` + `retry.ts`

AI 调用会以各种方式失败。这套设计的核心是：**先把五花八门的错误归成有限的几个「kind」，再由 kind 决定「重试还是放弃」。**

```
ClassifiedProviderError.kind ∈
  transient       —— 临时（500/过载/网络）      → 重试
  rate_limit      —— 限流（429）                → 按 Retry-After 重试
  quota_exhausted —— 额度耗尽                    → 不重试（换策略/暂停）
  auth_invalid    —— 密钥无效（401/403）         → 不重试（要人改配置）
  setup_required  —— 可执行文件缺失/太旧          → 不重试（要人装环境）
  unrecoverable   —— 400/上下文超长/模型非法      → 不重试（重试也没用）
```

各 Provider 有各自的分类函数（`classifyClaudeError` / `classifyGeminiError`…），因为信号来源不同：Claude 看 SDK 错误类名和 Anthropic 的消息串；Gemini 看 HTTP status 和响应体里的 `quota exceeded` 等标记。但**产物统一是 `ClassifiedProviderError`**。

`retry.ts` 的 `withRetry` 消费这个 kind：

- `isRetryableKind`：只有 `transient` / `rate_limit` 才重试，其余立刻抛。
- **指数退避 + 抖动**：`100 * 2^attempt + random(50)`，封顶 30s。
- **上限只有 2 次**：因为对这些 API 的 POST 不严格幂等（尽力用请求 id 去重）。
- **可中止的 sleep**：退避等待期间收到外部 abort 立即退出，不傻等。

> 💡 对照第四层：那里坏数据在 Zod 边界被挡下；这里坏调用在分类边界被归类。**「先归一，再决策」是这个代码库反复用的套路**——把不可控的外部世界（各平台方言、各家 API 错误）先翻译成自己的有限词汇表，后续逻辑就干净了。

### 16.4 一个小而实用的设计：`model-aliases.ts`

`resolveTierAlias` 让用户在设置里写**可移植的层级别名**而非具体模型名：

```
$TIER:fast    → 配置的 fast 模型（默认 haiku）
$TIER:smart   → 默认 sonnet
$TIER:summary → 专门的总结模型，没配就回落默认模型
```

且**在「请求时」解析、而非「加载设置时」**——用户改了设置不必重启 worker。纯函数、不改动 settings。小功能，但体现了「配置的可移植性 + 热更新」的考量。

> ✅ **本步小结**：三个 Provider（Claude 走 SDK 子进程、Gemini/OpenRouter 走 HTTP）共享同一套提示词与解析器，`getSelectedProvider` 按设置择一。`ClaudeProvider` 用「消息生成器喂 query + 消费流」模型跑一个长观察者会话（init 立人设 → 逐条 observation → summarize）。容错靠「先分类（`ClassifiedProviderError.kind`）、再由 kind 决定重试（`withRetry` 指数退避）」。`model-aliases` 提供请求时解析的可移植层级别名。

## 回到主线：一条 observation 的完整诞生

把三步接起来，走一遍你「编辑一个文件」后台发生的事：

```
你在 Claude Code 里 Edit 了 foo.ts
  │
  ├─(A) hook 路径：PostToolUse 回调 → POST /api/sessions/observations   ┐
  └─(B) 监听路径：watcher 追到 .jsonl 新行 → processor → ingestObservation ┘ 两路同归
  │
  ▼  worker 把这条工具活动排进「观察队列」（= 第四层的 AgentEvent 形状）
  │
  ▼  ClaudeProvider 的消息生成器取出它
     → buildObservationPrompt：包装成给观察者的提问（超大字段先截断）
  │
  ▼  锁死的 Observer 模型（hardened-options）读完这段活动，吐一段 <observation> XML
  │
  ▼  parseAgentXml 解析 → ParsedObservation（type/title/facts/files_modified…）
     （若是大白话/空/限额 → output-classifier 分类，记 warn 或转可恢复暂停）
  │
  ▼  ResponseProcessor.storeObservations → 落库（= 第四层的 MemoryItem）
     → 异步 syncObservation 到 Chroma（= 第六层向量检索的底座）→ 广播/通知
```

**这一层让你看清了那个一直含糊的「压缩」到底是什么**：它是一次由锁死观察者模型完成的「读原始活动 → 吐结构化 XML」的翻译，两端各有一道校验闸（提示词截断 / 解析校验），外面裹着多 Provider 容错。进去的是 `AgentEvent`，出来的是 `MemoryItem`——第四层的那两种货物，在这里被真正地「加工」了一次。

## 本层结束自测

1. **claude-mem 的「压缩」本质上是什么？** → 一次 AI 调用：worker 启动一个被彻底锁死（零工具）的 Observer 模型，让它把原始工具活动提炼成 `<observation>` XML。不是普通字符串处理。
2. **已经有 hook 了，为什么还要 transcript 监听？** → hook 面向原生支持回调的 Claude Code；监听面向没有 hook 的平台（如 Codex），用声明式 schema 抹平各家 `.jsonl` 格式差异。两条路最终汇入同一个 worker 观察队列。
3. **worker 重启后为什么不会重复压缩已读过的会话记录？** → `watcher` 把每个文件读到的偏移量持久化在 `state.ts`（`transcript-watch-state.json`），重启后从断点续读；文件被截断时 offset 归零自愈。
4. **一次 `Read` 读了 13 万字符的大文件，会不会把观察者的上下文撑爆？** → 不会。`truncateObservationField` 把单字段截到 16k 字符（头 60%/尾 30%），中间用 `<elided/>` 标记替换，并提示模型不要编造被省略的部分。
5. **模型返回一句大白话而非 XML，会怎样？** → `output-classifier` 把它归为 `prose`（或 `idle`/quota），记一条带预览的 warn 而非静默丢弃；若识别为限额提示，则暂停生成、保住未压缩的观察等待恢复。
6. **Claude API 返回 401 和返回 500，处理有何不同？** → 都先被分类成 `ClassifiedProviderError`：401 → `auth_invalid`（不重试，要人改配置）；500 → `transient`（`withRetry` 指数退避重试，上限 2 次）。
7. **Observer 会不会趁机改我的代码？** → 不会。`hardened-options.ts` 用六层防御（`tools:[]` + 拒绝名单 + `permissionMode` + `canUseTool` 拒绝并审计 + 文件/MCP/设置隔离）把它锁成零工具，任何工具调用都被拒并写审计日志。

七题能答上来，写入主线就通了。下一层 **第六层** 走主线的后半段——这些落好库、同步进 Chroma 的记忆，是**怎么被检索回来、注入进下一次会话**的。
